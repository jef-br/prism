### T-5020 · Folder names never reach the matcher
**Status:** Ready | **Profile:** P1-feature-worker

An image's folder is often the only thing that identifies it — `1.jpg` inside `26182-Denim-801/` is
useless on its own and unambiguous with its folder. `FolderNameEnricher` exists to borrow that folder
name. Today it can never do so through the normal job path, and even when it is reached it fails on
one of the two folder shapes in `test/datasets/JBComplete/`.

Three separate causes. All three must be fixed for the feature to work end to end.

**1. The test runner throws the folder away before upload.**
`test/test-scripts/PrismJobRunner.psm1`:
- `Get-PrismJobInputFiles` de-duplicates by *leaf filename* (`$seen.Add($file.Name)`), so
  `26182-Denim-801/1.jpg` and `foldercontainsID99984905/1.jpg` collide on `1.jpg` and the second is
  **silently dropped**.
- `Submit-PrismJob` uploads each part as `[Path]::GetFileName($path)` and packs ZIP entries with
  `CreateEntryFromFile(..., GetFileName($img), ...)`.

**Effect:** a JBComplete run loses 2 images outright and delivers the other 7 with no folder.

**2. The core ZIP reader strips member folders.**
`jb/src/core/lib/Zip/ZipHandler.cs:190` — `string originalFileName = Path.GetFileName(memberPath);`
So a ZIP member's `InitialFullName` is always a bare filename. Since the runner routes everything
except one seed image through a repacked ZIP, folder structure would still be lost even with (1)
fixed. `FolderNameEnricher.GetFolderPath` returns null when the name has no slash, so the enricher
cannot fire at all.

**3. `MeaningfulTokens` keeps a mixed letter+digit run whole and skips the split.**
`jb/src/core/Services/Matching/Match/FolderNameEnricher.cs:161-164` adds the whole run and `continue`s
past the letter↔digit split below it. Measured against the real Excel rows (scratch probe, run
2026-08-04):

| Folder | Alias assigned? |
|---|---|
| `26182-Denim-801/` | **yes** — `26182-Denim-801 1.jpg` |
| `foldercontainsID99984905/` | **no** |
| `99984901/` | no (correct — the filenames already carry the ID) |

`foldercontainsID99984905` produces exactly one token, `foldercontainsid99984905`, which is not in the
Excel vocabulary. The probe confirms `99984905` **is** in the vocabulary (it is the FamilyID), so the
failure is entirely on the folder-token side. Expected tokens are `foldercontains` and `99984905`;
splitting `foldercontains` further into `folder` + `contains` is explicitly out of scope for now.

**What to do:**
- [ ] Carry the path relative to the submitted root all the way through: runner de-dup key, multipart
      part name, ZIP entry name, and `ZipHandler`'s `originalFileName`.
- [ ] Make the duplicate decision use the full path plus the other signals that already exist (visual
      hash, pixel dimensions, byte length) rather than the leaf name alone. Two files called `1.jpg`
      in different folders are not duplicates; `4471-2290-F - Copy.jpg` is.
- [ ] In `MeaningfulTokens`, emit the letter↔digit split **in addition to** the whole run, not instead
      of it. Keep `SH23005` working (`MatcherUpgradeTests.FolderNameEnricher_MeaninglessFileInMeaningfulFolder_BorrowsFolderName`).
- [ ] Consider also emitting the separator-stripped concatenation of digit runs (`26182-801` →
      `26182801`) on both the folder side and the Excel vocabulary side, so a folder written without
      the separator still resolves. Not required for JBComplete to pass — `26182` alone already
      carries it — so treat as a judgement call, not a given.
- [ ] Re-run the probe. Then add the 9 subfolder images to `test/datasets/JBComplete/expected-match.json`
      (they are labelled in `expected-phenotype.json` already but held out of the match golden).

**Files:** `test/test-scripts/PrismJobRunner.psm1`, `jb/src/core/lib/Zip/ZipHandler.cs`,
`jb/src/core/Services/Matching/Match/FolderNameEnricher.cs`, `jb/src/core/lib/Ingress/Importer.cs`,
`test/datasets/JBComplete/`.
