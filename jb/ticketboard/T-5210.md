### T-5210 · SiblingPropagator may reinvent token evidence Brackets 1-3 already built
**Status:** Ready | **Profile:** P3-scout
**Found by:** [[T-5200]] investigation, 2026-08-11 — live-observing the SMASHEDLEMON45 hang.

**The observation.** `SiblingPropagator.BuildProfile` (`SiblingPropagator.cs:197-211`) derives its own
rare-token profile from `record.MatchingName` via regex — split on separators and letter↔digit
boundaries, drop shot-suffix tokens and tokens under 2 chars. It does not read
`MatchEvidence.NumericTokenEvidence` or `.StringTokenEvidence`, which Brackets 1-3 already attach to
every matched record before `SiblingPropagator.Run` is ever called. The profile is rebuilt from
scratch, by regex, for every matched *and* every unmatched record, on every call.

**The open question — investigate before assuming either answer.** Is this pure duplication (the
existing token evidence already carries what `BuildProfile` needs, and `SiblingPropagator` should
consume it instead of re-deriving it), or a genuine shape mismatch? `BuildProfile`'s own doc comment
(`SiblingPropagator.cs:7-13`) describes a "rare token profile" concept with batch-noise removal
(`CommonTokenRatio`/`CommonTokenFloor`, `RemoveBatchCommonTokens`) that `NumericTokenEvidence`/
`StringTokenEvidence` may not carry in the same form — those are pairwise (filename token ↔ Excel
family token) evidence records, not a per-image rare-token set. Read both sides closely — what shape
each existing evidence type actually has, and what `BuildProfile` needs — before concluding either
way. Check git history/`PRISM-match.md` for why the separate tokenizer was introduced originally, if
findable.

**Why this needs its own ticket, not a line in [[T-5200]].** This is a reuse/architecture question
(does the code already have what it needs and ignore it), not an algorithmic-complexity question (how
expensive is the O(n²) shape). CLAUDE.md's standing rule is to reuse existing code before inventing
new code; this session's own first pass on `SiblingPropagator` confirmed the O(n²) shape but missed
this reuse gap entirely until the user flagged it directly — worth a dedicated look precisely because
it's the kind of check that's easy to skip when focused on complexity alone.

**If confirmed as duplication**, this feeds directly into T-5200's fix: eliminating a full
re-tokenization pass removes real per-comparison cost on top of whatever indexing/filtering T-5200
lands on. Do not prescribe the fix here — that's for whichever ticket implements it once the shape
question is answered.

**Acceptance:** a written answer (in this ticket or `PRISM-match.md`) stating whether
`SiblingPropagator`'s token profile can be built from existing `MatchEvidence` token evidence, what
would have to change if not, and — if it's genuine duplication — a decision on whether to fix it here
or fold into [[T-5200]]'s implementation pass.
