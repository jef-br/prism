### T-5210 · SiblingPropagator may reinvent token evidence Brackets 1-3 already built
**Status:** Ready | **Profile:** P3-scout
**Found by:** [[T-5200]] investigation, 2026-08-11 — live-observing the SMASHEDLEMON45 hang.

`SiblingPropagator` builds its own rare-token profile via regex on every call instead of reading the
pairwise token evidence Brackets 1-3 already attach to matched records. This ticket investigates
whether that's pure duplication PRISM should eliminate, or whether the two token shapes genuinely
differ and the separate pass is required. A duplication finding would feed directly into T-5200's fix.

**Problem(s):**
- `SiblingPropagator.BuildProfile` (`SiblingPropagator.cs:197-211`) derives its own rare-token profile
  from `record.MatchingName` via regex — split on separators and letter↔digit boundaries, drop
  shot-suffix tokens and tokens under 2 chars — instead of reading `MatchEvidence.NumericTokenEvidence`
  or `.StringTokenEvidence`, which Brackets 1-3 already attach to every matched record before
  `SiblingPropagator.Run` is ever called. The profile is rebuilt from scratch, by regex, for every
  matched and every unmatched record, on every call.
- This is its own ticket rather than a line in [[T-5200]] because it's a reuse/architecture question
  (does the code already have what it needs and ignore it), not an algorithmic-complexity question (how
  expensive the O(n²) shape is) — CLAUDE.md's standing rule is to reuse existing code before inventing
  new code. This session's own first pass on `SiblingPropagator` confirmed the O(n²) shape but missed
  this reuse gap entirely until the user flagged it directly, which is exactly why it's worth a
  dedicated look: it's the kind of check that's easy to skip when focused on complexity alone.

**Decision(s):**
- Open — is this pure duplication (the existing token evidence already carries what `BuildProfile`
  needs, so `SiblingPropagator` should consume it instead of re-deriving it), or a genuine shape
  mismatch? `BuildProfile`'s own doc comment (`SiblingPropagator.cs:7-13`) describes a "rare token
  profile" concept with batch-noise removal (`CommonTokenRatio`/`CommonTokenFloor`,
  `RemoveBatchCommonTokens`) that `NumericTokenEvidence`/`StringTokenEvidence` may not carry in the same
  form — those are pairwise (filename token ↔ Excel family token) evidence records, not a per-image
  rare-token set. Investigate before assuming either answer: read both sides closely for what shape each
  existing evidence type actually has and what `BuildProfile` needs, and check git history/
  `PRISM-match.md` for why the separate tokenizer was introduced originally, if findable. If confirmed
  as duplication, it feeds directly into T-5200's fix — eliminating a full re-tokenization pass removes
  real per-comparison cost on top of whatever indexing/filtering T-5200 lands on — and also requires
  deciding whether to implement the fix in this ticket or fold it into T-5200's implementation pass; do
  not prescribe the fix mechanics themselves here.

**Test(s):**
- Deliverable: a written answer, in this ticket or `PRISM-match.md`, stating whether
  `SiblingPropagator`'s token profile can be built from existing `MatchEvidence` token evidence, what
  would have to change if not, and — if it's genuine duplication — the decision on whether to fix it
  here or fold it into T-5200's implementation pass. Not yet written (open).
