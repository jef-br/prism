### T-5090 · SubstringRescue glues the shot number onto the reference and matches into a longer EAN
**Status:** Ready | **Profile:** P1-feature-worker
**Review:** Request Changes (2026-08-11) — the `NumericMatcher.cs` fix itself is correct and well
tested (275/275 green on a clean `Prism.Services.Matching.Tests` run, dedicated regression test for
the exact `87186790_1`/`_2` shape, existing single-token-rescue test still passes unmodified). What's
missing: the ticket's own Acceptance line requires JBComplete's other SubstringRescue matches (5 total
per T-3800's measurement, of which this pair is 2) to be re-checked for the same welded-token accident
and any findings reported — the "Implemented" note only verifies the two images named in the ticket
and the aggregate CiMini mismatch count, it does not address this per-match re-check. Closing without
it repeats exactly the "resolved by accident, not reported" pattern this ticket exists to stop.
**Found by:** scoring JBComplete `-Mode Match` against its golden, 2026-08-05. Real defect — the
dataset README calls this case "must reject".

`NumericMatcher.TryMatchBySubstringRescue` let a shot-number suffix weld onto a product reference,
letting a polluted longer token resolve first and match into the wrong EAN with high confidence
instead of correctly refusing. The core fix (Option 2 below) landed 2026-08-11 and is verified on the
two images that surfaced the bug — the ticket stays open only because its Acceptance line also
requires re-checking JBComplete's other SubstringRescue matches for the same bug class, and that
re-check was never done.

**Problem(s):**
- Two images of one product resolved to two different FamilyIDs via SubstringRescue, when the golden
  (`test/datasets/CiMini/README.md` §6.2) expects `MATCH_NOT_FOUND` for both, because `87186790` is a
  prefix of two EANs and the picture matches neither garment:

  | Image | Got | Accepted explanation |
  |---|---|---|
  | `87186790_1.jpg` | `99984905` | `SubstringRescue: token '871867901' is contained in target '8718679018555'` |
  | `87186790_2.jpg` | `99985047` | `SubstringRescue: token '871867902' is contained in target '8718679021272'` |

  Cause: the monotoken is built as `string.Concat(stem.Where(char.IsDigit))`, which welds the
  shot-sequence suffix onto the product reference (`87186790_1` → `871867901`), then rescue tokens are
  tried `OrderByDescending(t => t.Length)`, so the polluted 9-digit token goes first. Effect: the
  honest 8-digit token `87186790` is contained in *both* EANs and would correctly produce
  `containingFamilies.Count == 2` (refused), but it's never reached — the polluted token is tried
  first and happens to be contained in exactly one EAN (whichever one has that shot digit in the 9th
  position), so `_1` and `_2` each pick a different EAN by accident. Consequence: appending a shot
  number fabricates evidence instead of narrowing it, and the split is silent — `FinalScore` is the
  configured `SubstringRescueConfidence` (0.9), no KO/warning/near-tie is recorded — so a wrong family
  reaches the output filename at high confidence, which is worse than a miss. Not dataset-specific: any
  catalogue using `<reference>_<n>.jpg` naming where references are prefixes of longer barcodes hits
  this, and that's the common naming case.

**Decision(s):**
- Shape of the fix — two options were on the table: (1) build the monotoken from the reference part of
  the stem only, stopping at the first separator followed by a short digit run (e.g. `87186790_1` →
  `87186790`) — narrow, but "short digit run after a separator" is itself another heuristic to
  calibrate; (2) evaluate *every* rescue token and refuse the image when two tokens rescue to different
  families, instead of returning on the first token that resolves uniquely — removes the dependency on
  `OrderByDescending(Length)`, which is the actual fragility, and turns a silent wrong answer into the
  KO the golden asks for. **(decided: Option 2, implemented 2026-08-11)** — `TryMatchBySubstringRescue`
  now evaluates every rescue token and requires all of them to agree: any single token that's ambiguous
  on its own (2+ families) disqualifies the image outright, and a more "precise" welded token cannot
  override that by intersection. A subtlety found while implementing: naive per-token intersection lets
  a unique 9-digit welded token silently narrow away the ambiguity of the honest 8-digit reference,
  reproducing the original bug in a different shape — the implementation guards against this by
  disqualifying on any single ambiguous token rather than intersecting candidate sets.
- Whether the shot number should be deleted or kept, corrected 2026-08-07 (origin: session on
  det-ordering and filename tokens, the same session that produced [[T-5120]] and reverted [[T-5060]]).
  User direction: `87186790_1` must yield all three forms — `87186790`, `1`, and `871867901` — each
  used for what it's good for; the defect is not "the shot number exists", it's "the welded token is
  tried first and allowed to answer alone", so the fix must fix precedence, not delete tokens. Verified
  against code the same day: the split already happens (`GetNumericTokensFromFilename` splits the stem
  into digit runs, so `87186790` and `1` both exist; `string.Concat(stem.Where(char.IsDigit))` builds
  `871867901`), but `GetEligibleTokens` filters to `minNumericTokenLength` (5, in `MatchingConfig.json`),
  so `1` never reaches a matcher as evidence — it survives only as glue inside Bracket 2's concatenation
  loop, matching the in-code comment's stated intent that "a shot suffix like `_01` must not act as
  standalone evidence." **(decided: that intent is right for matching, wrong for ordering)** — `1` must
  never identify a product (it would match anything), but it's exactly the signal [[T-5120]] wants for
  det order, so the token needs to survive with a label saying what it is (sequence marker) instead of
  being dropped for being short; a consumer then chooses — the matcher ignores it, the orderer uses it.
  Example: `87186790_1.jpg` → `87186790` is product evidence, `1` is order evidence, `871867901` is
  neither and should only be trusted when nothing shorter resolves. Counter-example:
  `8718679021272.jpg` — one unbroken run, no sequence marker at all, nothing here applies, don't invent
  a trailing digit by splitting a real EAN. Scope: not implemented in this ticket — Option 2 above still
  stands as this ticket's fix; this decision only records that the fix must not discard the shot number
  on its way out, because [[T-5120]] needs it.
