### T-5090 · SubstringRescue glues the shot number onto the reference and matches into a longer EAN
**Status:** Ready | **Profile:** P1-feature-worker
**Found by:** scoring JBComplete `-Mode Match` against its golden, 2026-08-05. Real defect — the
dataset README calls this case "must reject".

**Two images of one product came back with two different FamilyIDs:**

| Image | Got | Accepted explanation |
|---|---|---|
| `87186790_1.jpg` | `99984905` | `SubstringRescue: token '871867901' is contained in target '8718679018555'` |
| `87186790_2.jpg` | `99985047` | `SubstringRescue: token '871867902' is contained in target '8718679021272'` |

Golden expects `MATCH_NOT_FOUND` for both (`README.md` §6.2: `87186790` is a prefix of two EANs, and
the picture matches neither garment).

**Cause, exactly.** `NumericMatcher.TryMatchBySubstringRescue` builds its rescue tokens like this:

```
string fileDigits = string.Concat(stem.Where(char.IsDigit));   // "87186790_1" -> "871867901"
string[] rescueTokens = tokens.Concat(...[fileDigits])
    .Where(t => t.Length >= this.substringRescueLength)
    .OrderByDescending(t => t.Length)                          // the polluted token goes FIRST
```

The monotoken concatenates every digit in the stem, so the **shot-sequence suffix is welded onto the
product reference**: `87186790` + `1` = `871867901`. The loop then tries the longest token first.

**Effect.** The honest token `87186790` is contained in *both* EANs, so it would have produced
`containingFamilies.Count == 2` and been correctly refused. It is never reached, because the
9-digit polluted token is tried first and is contained in exactly one EAN — the one whose 9th digit
happens to be `1`. `_2` then picks the other EAN by the same accident.

**Consequence.** Appending a shot number does not narrow evidence, it fabricates it. Two images of
one product are split across two families, and the split is silent: `FinalScore` is the configured
`SubstringRescueConfidence` (0.9), and no KO, warning or near-tie is recorded. This is worse than a
miss — a wrong family with high confidence flows all the way to the output filename.

**Not dataset-specific.** Any catalogue using `<reference>_<n>.jpg` naming where references are
prefixes of longer barcodes hits this, and that naming is the common case.

**Shape of the fix (pick one, both are contained):**
1. Build the monotoken from the reference part of the stem only — stop at the first separator that is
   followed by a short digit run, so `87186790_1` yields `87186790`. Narrow, but "short digit run
   after a separator" is another heuristic to calibrate.
2. Evaluate **every** rescue token and refuse the image when two tokens rescue to different families,
   instead of returning on the first token that resolves uniquely. Ordering stops mattering, and the
   contradiction between `871867901`→`99984905` and `87186790`→{two families} becomes visible.

Option 2 is preferred: it removes the dependence on `OrderByDescending(Length)`, which is the actual
fragility here, and it turns a silent wrong answer into the KO the golden asks for.

**Acceptance:** `87186790_1.jpg` and `87186790_2.jpg` both KO with both candidate families named;
JBComplete's other 4 SubstringRescue matches (`NumericMatcher.SubstringRescue`, 5 total today) are
re-checked and any that were resolved by the same accident are reported, not silently kept.
