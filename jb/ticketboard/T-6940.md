### T-6940 · Match-only runs still pay for feature-analysis work matching never reads
**Status:** Ready | **Profile:** P1-feature-worker
**Found by:** [[T-6910]] / [[T-6900]], 2026-08-11 — split out on close so it isn't lost in the archive.

Match-only runs (`SkipClassification=true`) still pay the full decode/hash/feature-analysis cost even though matching never reads that output. Split out from T-6910/T-6900 on close so the finding isn't lost in the archive.

**Problem(s):**
- `PrismProcessingParameters.SkipClassification=true` (a match-only run) gates CLIP off via `doClassify`, but decode, hashing, and `ImageFeatureAnalyzer.Analyze`/`Refine` all run regardless — matching itself never reads their output. Measured on SMASHEDLEMON45 (1774 images, 13,130 MP): feature analysis alone costs ~64 CPU-minutes spent on measurements a match-only job has no use for. This isn't hypothetical — T-6900's SMASHEDLEMON45 measurement was a match-only run and paid this cost in full, a meaningful fraction of that job's 36-minute wall clock.

**Decision(s):**
- Shape of the fix is undecided: a genuine match-only fast path that skips decode/hash/analyze entirely when `SkipClassification=true` and no downstream stage needs feature data. Needs a check for which downstream consumers (Transform routing, phenotype rules) actually require Classified-stage features even on a match-only run — if any do, this can't be a blanket skip.

**Test(s):**
- Acceptance: a match-only SMASHEDLEMON45-scale run measurably drops in wall clock; a run that also needs Classify/Transform is unaffected; no output changes for any non-match-only run.

**Files:** `jb/src/core/Services/Matching/MatchingService.cs` (`PrepareLambda`, the `doClassify` gate).
