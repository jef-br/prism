### T-5130 · Excel column-fill-rate gate drops sparse description columns before any matcher sees them
**Status:** Ready | **Profile:** P1-feature-worker
**Found by:** [[T-5110]], 2026-08-11 — the FilenameToCellMatcher cell-scanning fix was verified correct
in isolation but could not be verified end-to-end on CiMini's own `100267_*` case because of this,
unrelated, upstream gap.

The Excel fill-rate gate silently drops a sparse-but-real filename-reference column before any matcher
can see it, blocking end-to-end verification of the T-5110 fix on CiMini's own case. The 20% threshold
itself isn't the bug — it exists to keep noisy near-empty columns out of the model
(`jb/docs/PRISM-excel.md` § Column Validity). This ticket is to decide what should happen for a column
shaped like this, not to unilaterally pick a new ratio.

**Problem(s):**
- `ModelBuilder.ColumnHasEnoughUsefulValues` (`jb/src/core/lib/Excel/ModelBuilder.cs:542`) drops any
  non-PK column where fewer than `ExcelConfig.json`'s `ColumnValidity.MinimumUsefulValueRatio` (currently
  `0.2`, i.e. 20%) of rows have a value, before `FamilyIDRecord.MergeProperty` ever runs on it. CiMini's
  marketing-description column has exactly one filled cell across ~34 family rows (~3% fill) — the one
  row this ticket needs — so the whole column is excluded at ingestion. Effect: no matcher, not just
  `FilenameToCellMatcher`, can ever see that cell's data; the drop happens upstream of the entire
  Matching stage.
- Beyond CiMini, this is a plausible production shape, not a synthetic one: a marketing-description or
  notes column that names images on only a few rows (the rest of the sheet using structured columns
  instead) is a realistic catalogue-export pattern — most rows don't need free-text image references but
  a few edge-case rows do.

**Decision(s):** decide between the following (tradeoffs are real, do not guess):
1. Lower `MinimumUsefulValueRatio` — widens what other sparse, possibly-noisy columns get indexed too.
2. Exempt description/notes-shaped columns from the fill-rate gate specifically (needs a rule for what
   counts as "description-shaped").
3. Keep the gate but let `FilenameToCellMatcher` (and any other last-resort bracket) read from raw,
   ungated cell data directly rather than only the post-`ModelBuilder` model — a scope change to where
   Bracket 5 sources its candidates.
4. Something else — flag if none of the above fit.

**Test(s):**
- Confirmed live (T-5110): the built `FilenameToCellMatcher` index is 0 keys for the whole batch, and
  `unzip -p Brackets-Complete.xlsx xl/sharedStrings.xml` shows the cell text is present in the source
  file and contains exactly the filenames needed. (run: confirmed, 2026-08-11)
- Acceptance: a decision recorded in `jb/docs/PRISM-excel.md`'s Column Validity section; CiMini's seven
  `100267_*` rows resolve via `FilenameToCellMatcher` (or explicitly remain `MATCH_NOT_FOUND` if the
  decision is "do not fix"); no currently-passing CiMini golden row regresses. Not yet run.
