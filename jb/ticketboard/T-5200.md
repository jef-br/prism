### T-5200 · SiblingPropagator loose-relation pass is unindexed O(unmatched × matched)
**Status:** Ready | **Profile:** P1-feature-worker
**Found by:** BE-tests matching-only run, 2026-08-10 — `X SMASHEDLEMON45` (1774 images) timed out at
45 minutes (JobID `3ddf1ad1-56d8-44b2-a36e-aaeddc9ab7d3`, `TIMEOUT_OR_NO_RESULT`). See
`matching-testlogs.txt` "ROUND 2" entries.

**The problem.** `SiblingPropagator.Run` (`jb/src/core/Services/Matching/Match/SiblingPropagator.cs:62`)
calls `FindLooseRelation` (line 146) once per unmatched image; `FindLooseRelation` does a full linear
scan over every matched sibling's rare-token profile with no index. That is O(unmatched × matched)
per job, each comparison doing `HashSet` subset/intersection work — no early exit, no bucketing by
token. At thousands of images this can blow up; the exact SMASHEDLEMON45 job never returned in 45
minutes even in match-only mode (classification skipped, so CLIP/Bracket 4/5 were never in play).

**Confirmed by live observation, 2026-08-11.** A third real run (JobID
`51970db6-6dc5-4744-82fe-289e91ea251c`) was watched end-to-end instead of left to time out blind:
`Prism.Api.exe` burned sustained multi-core CPU for ~28 minutes (CPU time climbing ~85-90s per 30s
wall-clock interval, i.e. 3+ cores continuously busy) with working-set oscillation consistent with GC
churn from allocation-heavy set operations, zero SSE progress events (`ImageMatcher.RunWaterfall`
emits none — the whole Match stage is a black box until it returns), and zero partial result. The job
was killed rather than let run out the remaining time to a certain third timeout. Combined with
process-of-elimination over the rest of the waterfall — Brackets 1, 2, 2-Intersect, 3,
FilenameToCell, and SubstringRescue are each a single O(n) or bounded-per-record pass over ~1774
filenames, none of which can plausibly take minutes — `FindLooseRelation` remains the only
O(unmatched × matched) pass in the whole waterfall and is now a strong live-observed match, not just a
structural risk. **What is still missing:** a line-level profiler trace or instrumented per-bracket
timing split. This evidence is behavioral/correlational (CPU/GC signature + elimination), not a
captured stack sample — stated plainly so this isn't overclaimed as proof.

**Possible interaction with T-2840 — measured, and downgraded to low risk, 2026-08-11.**
`ImageMatcher.RunWaterfall` gates Bracket 4 (`SemanticMatcher`, CLIP-driven) on
`allRecords.Any(r => r.Tags.Influential.Length > 0)` (`ImageMatcher.cs:98`). In match-only mode
(`SkipClassification=true`, what every BE-tests run used, including all three SMASHEDLEMON45
timeouts) that condition is always false, so Bracket 4 never runs — T-2840 is structurally excluded
from these specific runs and does not explain the observed hang. The theoretical link, for whenever
classification is on: if Bracket 4's candidate set is unstable, that changes how many images spill
into SiblingPropagator. T-2840's isolated-batch experiment measured the actual instability: max
single-image confidence delta 0.045, signed range 0.069 across one family — small enough that the
user's direction on T-2840 is to fix it by calibrating thresholds well clear of that band, not by
chasing the batching mechanism. **Once that calibration lands, Bracket 4's accept/reject/tie-break
outcomes become stable again and this compounding risk mostly goes away** — a threshold with enough
margin over ~0.07 of jitter can't flip on batch composition alone. Until the calibration lands, treat
this as a residual, currently-quantified risk rather than an open unknown: the unmatched pool
SiblingPropagator sees could still shift by roughly the same few-percent-of-batch margin T-2840
measured, not an unbounded amount.

**Fix direction once confirmed:** index matched profiles by token (inverted index: token → matched
records carrying it) so a loose-relation lookup for one unmatched image only scans matched records that
share at least one rare token, not the full matched set. **Two complementary reuse opportunities found
2026-08-11, to weigh alongside the inverted-index approach:**
1. `SiblingPropagator.BuildProfile` (`SiblingPropagator.cs:197-211`) re-derives its own token set from
   the raw filename via regex rather than reading `MatchEvidence.NumericTokenEvidence`/
   `.StringTokenEvidence`, which Brackets 1-3 already populate. Whether this is pure duplication or a
   genuine shape mismatch (its "rare token profile" concept includes `CommonTokenRatio`/
   `CommonTokenFloor` batch-noise removal that the existing token evidence may not carry) is now its
   own ticket — see [[T-5210]] — and should be resolved before or alongside this fix, not folded in
   silently.
2. `crossBracketCandidates` (`ImageMatcher.cs:71`, accumulates every FamilyID each image was a
   near-miss candidate for across Brackets 1-4/FilenameToCell/SubstringRescue) is built one line above
   `siblingPropagator.Run` (`ImageMatcher.cs:112`) and never passed in. Threading it through would let
   `FindLooseRelation` skip matched records outside an unmatched image's own candidate families before
   ever building a profile to compare — narrowing the O(unmatched × matched) scan by candidate-family
   membership, independent of (and combinable with) the inverted-index approach.

Work this with `/pair` (repo convention: matching/ranking algorithm design, not plumbing). T-2840's
isolated-batch result is in hand (see the interaction note above) — batch instability is small and
being addressed by threshold calibration, so this fix does not need to defensively size itself against
a large or unbounded swing in the unmatched pool.

**Explicit scope boundary:** this ticket is about the algorithm, not about capping or timing out the
job. **Update 2026-08-11:** a configurable pipeline-level job timeout was attempted this session and
reverted — architecturally too complex to safely interrupt a stuck synchronous matching loop (no
`CancellationToken` checks exist anywhere in the matching code path; a timeout could only fire between
stages, not inside one). The user is relying on the existing `test/test-scripts/*.ps1` runner's own
client-side `-TimeoutMinutes` for now. Do not reintroduce a pipeline-level timeout without a plan for
actually interrupting synchronous matching work.
