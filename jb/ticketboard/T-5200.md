### T-5200 · SiblingPropagator loose-relation pass is unindexed O(unmatched × matched)
**Status:** Ready | **Profile:** P1-feature-worker

**Review:** Request Changes (2026-08-11) — the inverted-index part of commit `0e872fb` is provably
behavior-preserving (subset/superset relatedness on non-empty profiles always implies a shared token,
so the token-index can only prune candidates `IsSubsetOf` would reject anyway), but the
`crossBracketCandidates` threading is a real semantic narrowing of which matched siblings get compared,
not pure perf, and its filtering branch (`SiblingPropagator.cs:222-227`) is never exercised by any test
— all 4 updated `SiblingPropagator` unit tests pass a permanently-empty `NoCrossBracketCandidates`, and
no other test in the suite populates it either. Given this repo's own history of silent-wrong-match
defects in this exact bracket area (T-5090/T-5100/T-5110), a new candidate-narrowing filter shipping
with zero coverage of its actual filtering behavior needs at least one test before merge. Separately,
the claimed complexity win has no direct measurement — the only large-scale verification run
(SMASHEDLEMON45) never reached `SiblingPropagator` at all, per T-6900's own finding, so the perf
benefit is theoretically sound but empirically unverified. The scope boundary is handled correctly:
neither this ticket nor T-6900 overclaims that the fix resolves the hang.
**Found by:** BE-tests matching-only run, 2026-08-10 — `X SMASHEDLEMON45` (1774 images) timed out at
45 minutes (JobID `3ddf1ad1-56d8-44b2-a36e-aaeddc9ab7d3`, `TIMEOUT_OR_NO_RESULT`). See
`matching-testlogs.txt` "ROUND 2" entries.

`SiblingPropagator`'s loose-relation pass was the leading suspect for the SMASHEDLEMON45 hang: an
unindexed O(unmatched × matched) scan. A code review flagged two gaps before merge (untested
candidate-narrowing filter, unmeasured perf win); an end-of-session pairing pass then implemented,
tested, and live-verified the fix — and found it does not actually explain the hang.

**Problem(s):**
- `SiblingPropagator.Run` (`SiblingPropagator.cs:62`) calls `FindLooseRelation` (line 146) once per
  unmatched image; `FindLooseRelation` does a full linear scan over every matched sibling's rare-token
  profile with no index — O(unmatched × matched) per job, each comparison doing `HashSet`
  subset/intersection work with no early exit or token bucketing. At thousands of images this blows up:
  the SMASHEDLEMON45 timeout in Found-by above never returned in 45 minutes even in match-only mode,
  where classification is skipped so CLIP/Bracket 4/5 are never in play. Confirmed by live observation
  2026-08-11 (a third real run, JobID `51970db6-6dc5-4744-82fe-289e91ea251c`, watched end-to-end rather
  than left to time out blind): `Prism.Api.exe` burned sustained multi-core CPU for ~28 minutes (~85-90s
  CPU per 30s wall-clock interval, i.e. 3+ cores continuously busy), working-set oscillation consistent
  with GC churn from allocation-heavy set operations, zero SSE progress events (`ImageMatcher.RunWaterfall`
  emits none — the whole Match stage is a black box until it returns), and zero partial result; the job
  was killed rather than run to a certain third timeout. Process-of-elimination over the rest of the
  waterfall (Brackets 1, 2, 2-Intersect, 3, FilenameToCell, SubstringRescue — each a single O(n) or
  bounded-per-record pass over ~1774 filenames, none plausibly minutes-long) leaves `FindLooseRelation`
  as the only O(unmatched × matched) pass in the whole waterfall — a strong live-observed match, not
  just a structural risk. Still missing: a line-level profiler trace or instrumented per-bracket timing
  split; the evidence is behavioral/correlational (CPU/GC signature + elimination), not a captured stack
  sample — stated plainly so this isn't overclaimed as proof.
- Per the Review above: the `crossBracketCandidates` filtering branch (`SiblingPropagator.cs:222-227`)
  was never exercised by any test — all 4 `SiblingPropagator` unit tests pass a permanently-empty
  `NoCrossBracketCandidates`, and no other suite test populates it either, so its actual filtering
  behavior (a real semantic narrowing, not pure perf) is unverified. **Not confirmed resolved**: the
  end-of-session verification (2026-08-11, see Test(s) below) re-ran the same 26 `MatcherUpgradeTests` /
  271 `Prism.Services.Matching.Tests` — including the same 4 `SiblingPropagator_*` cases — with no
  indication a new test populating real `crossBracketCandidates` was added. This specific review
  requirement is still open as of the last update.
- Per the Review above: the claimed complexity win had no direct measurement — the only large-scale
  verification run (SMASHEDLEMON45) never reached `SiblingPropagator` at all. **Confirmed true, and
  explained, at end of session (2026-08-11):** a live rerun of `X SMASHEDLEMON45` (1774 images,
  match-only, via new `test/test-scripts/Run_SMASHEDLEMON45.ps1`) still timed out twice — once at a
  10-minute client timeout, once at 8 minutes with temporary per-bracket `[T5200-TIMING]` instrumentation
  added. The instrumented run produced zero `[T5200-TIMING]` log lines for any bracket, including
  Bracket 1, while the API process kept burning ~3 cores continuously (46.5s CPU / 15s wall-clock
  sample) — the same live signature originally used to diagnose the hang. This proves
  `ImageMatcher.RunWaterfall` (and therefore `SiblingPropagator`) is never even entered during the hang;
  the perf win remains genuinely unmeasured because the code path is never reached, and the real
  bottleneck is upstream, in `MatchingService.cs`'s pre-match pipeline (per-image feature-analysis loop
  or `Deduplicate`/`FindDuplicates`, both O(n) or worse over 1774 images before `ImageMatcher.Run` is
  called at `MatchingService.cs:144`) — now tracked separately as [[T-6900]].
- **Possible interaction with T-2840 — measured, and downgraded to low risk, 2026-08-11.**
  `ImageMatcher.RunWaterfall` gates Bracket 4 (`SemanticMatcher`, CLIP-driven) on
  `allRecords.Any(r => r.Tags.Influential.Length > 0)` (`ImageMatcher.cs:98`). In match-only mode
  (`SkipClassification=true`, what every BE-tests run used, including all three SMASHEDLEMON45
  timeouts) that condition is always false, so Bracket 4 never runs — T-2840 is structurally excluded
  from these specific runs and does not explain the observed hang. The theoretical link, for whenever
  classification is on: if Bracket 4's candidate set is unstable, that changes how many images spill
  into `SiblingPropagator`. T-2840's isolated-batch experiment measured the actual instability: max
  single-image confidence delta **0.045**, signed range **0.069** across one family — small enough that
  the user's direction on T-2840 is to fix it by calibrating thresholds well clear of that band, not by
  chasing the batching mechanism. Once that calibration lands, Bracket 4's accept/reject/tie-break
  outcomes become stable again and this compounding risk mostly goes away — a threshold with enough
  margin over ~0.07 of jitter can't flip on batch composition alone. Until the calibration lands, treat
  this as a residual, currently-quantified risk rather than an open unknown: the unmatched pool
  `SiblingPropagator` sees could still shift by roughly the same few-percent-of-batch margin T-2840
  measured, not an unbounded amount. Open pending T-2840's threshold calibration.
- **Dead-end investigation, recorded so nobody re-does it (2026-08-11).** A prior CLIP "serialization"
  attempt was searched for and found not to exist in any recoverable form. The daily-brief (`daily-brief.md`)
  referenced reworking "how CLIP is used per image... now 300% slower due to serialization" tied to this
  investigation. Searched exhaustively: `main` history near T-2840's filing date (commit `6290608` adds
  only the ticket file, no code); the one CLIP-batching change that does exist (`76d6fd0`, 2026-07-03 —
  chunked inference, a deliberate speed-up a month before T-2840, doesn't match "slower"); the stranded
  `worktree-agent-af1130dfdbdc7b5c2` branch (no commits beyond main); `git stash list`; and remote branch
  `claude/wonderful-tesla-2qye1c` (one commit ahead of main, a daily-brief text edit only, same lineage
  otherwise). No commit anywhere contains a CLIP serialization/ONNX re-export change, and current
  `ImageClassifier.cs`/`ClassificationService.cs`/`MatchingService.cs` were read in full and carry no
  such artifact. Conclusion: the attempt was made directly in a working tree in a prior session and
  discarded before being committed — nothing to revert, current CLIP code is already clean. Closed;
  recorded only so a future reader doesn't re-search for it.

**Decision(s):**
- Fix direction (decided 2026-08-11): index matched profiles by token (inverted index: token → matched
  records carrying it) so a loose-relation lookup for one unmatched image only scans matched records
  that share at least one rare token, not the full matched set. Two reuse opportunities were weighed
  alongside it: (1) `crossBracketCandidates` (`ImageMatcher.cs:71`, accumulates every FamilyID each
  image was a near-miss candidate for across Brackets 1-4/FilenameToCell/SubstringRescue, built at
  `ImageMatcher.cs:112` one line above `siblingPropagator.Run` but never passed in) — threading it
  through would let `FindLooseRelation` skip matched records outside an unmatched image's own candidate
  families before ever building a profile to compare, narrowing the scan by candidate-family membership
  independent of (and combinable with) the inverted-index approach; (2) `SiblingPropagator.BuildProfile`
  re-deriving its own token set — spun off, see the T-5210 decision below. Work done with `/pair` (repo
  convention for matching/ranking algorithm design, not plumbing); T-2840's isolated-batch result (see
  Problem(s) above) meant the fix didn't need to defensively size itself against a large or unbounded
  swing in the unmatched pool. **Implemented 2026-08-11 (end of session):** the paired session delivered
  all three pieces — (a) fixed a genuine duplicate-work bug where `CountBatchTokens` and the
  matched/unmatched loops in `SiblingPropagator.Run` each independently rebuilt every record's
  rare-token profile via `BuildProfile`/regex, now built once per record and reused; (b) built the
  inverted index described above, narrowing `FindLooseRelation`'s candidate pool by token overlap
  before running the real `IsSubsetOf` check; (c) threaded `crossBracketCandidates` through
  `SiblingPropagator.Run`'s signature (now a third parameter) and `ImageMatcher.RunWaterfall`'s call
  site, filtering the token-index pool further by prior-bracket candidate-family membership when an
  entry exists, falling back to the unfiltered token-index pool when no entry exists (preserves recall
  for images no earlier bracket ever considered, per user decision during pairing).
- `SiblingPropagator.BuildProfile` (`SiblingPropagator.cs:197-211`) re-derives its own token set from
  the raw filename via regex rather than reading `MatchEvidence.NumericTokenEvidence`/
  `.StringTokenEvidence`, which Brackets 1-3 already populate. Whether this is pure duplication or a
  genuine shape mismatch (its rare-token profile concept includes `CommonTokenRatio`/`CommonTokenFloor`
  batch-noise removal that the existing token evidence may not carry) was spun off as its own ticket,
  [[T-5210]] (decided 2026-08-11), to be resolved before or alongside this fix rather than folded in
  silently. Deliberately left untouched this session — T-5210 is still open/unresolved, out of scope
  per this ticket's own instruction.
- Scope boundary (decided at ticket creation): this ticket is about the algorithm, not about capping or
  timing out the job. A configurable pipeline-level job timeout was attempted 2026-08-11 and reverted
  (decided against, 2026-08-11): architecturally too complex to safely interrupt a stuck synchronous
  matching loop — no `CancellationToken` checks exist anywhere in the matching code path, so a timeout
  could only fire between stages, not inside one. The user is relying on the existing
  `test/test-scripts/*.ps1` runner's own client-side `-TimeoutMinutes` for now. Do not reintroduce a
  pipeline-level timeout without a plan for actually interrupting synchronous matching work.
- **Disposition (decided 2026-08-11, end of session):** the three fixes above are real, tested
  improvements to `SiblingPropagator` (duplicate work removed, scan narrowed by token index + cross-
  bracket filtering) and are being committed as such. **They do NOT close this ticket's original
  SMASHEDLEMON45 hang** — per Problem(s) above, the live rerun proved the hang's actual cause sits
  upstream of `SiblingPropagator`/`ImageMatcher.RunWaterfall` entirely, in `MatchingService.cs`'s
  pre-match pipeline, and that root cause is now tracked separately as [[T-6900]]. This ticket is
  otherwise complete for its own stated scope (`SiblingPropagator.cs` + `ImageMatcher.cs` caller only —
  `MatchingService.cs` is explicitly out of bounds here by design, per the pairing session's scope
  boundary).
