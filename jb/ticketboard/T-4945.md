### T-4945 · Validate the hard-shadow threshold against labelled data + visual A/B
**Status:** Active | **Profile:** P1-feature-worker
**Found by:** [[T-4800]] SPACINI29 evidence run, 2026-07-28

Two calibration gaps in `SubjectDetector`, both needing data the repo didn't have at ticket creation:
the hard-shadow evidence threshold, and whether the promoted subject box centres as well as the legacy
salient box. `SubjectDetectionResult.HardShadowStrippedFraction` already carries the raw per-image
measurement for the first gap, so no re-instrumenting is needed there.

**Problem(s):**
- Hard-shadow threshold miscalibrated. `HardShadowEvidenceFraction` started at 0.01 — fired on 86/86
  SPACINI29 images, no discrimination, while trimming 6% off the bottom of every centred image. Raised
  to 0.05 against SPACINI29's own distribution (min 0.0113 / median 0.0371 / p90 0.0702 / max 0.1243,
  23/86 fire) — a reasoned choice on an *unlabelled* studio set, not ground truth. First labelled pass
  (2026-08-25, evidence harness, 6 CiMini images hand-edited hard in Photoshop, 5 measured — the
  `difficult shadows/` folder this ticket originally pointed at no longer exists, removed during the
  same day's golden recapture since none of its embedded IDs had a matching Excel row) found **0 of 5
  confirmed-hard images cross 0.05** (range 0.0096–0.0407) — confirms 0.05 was too high. Per-image data:

  | Image | `HardShadowStrippedFraction` | Subject confidence |
  |---|---|---|
  | `99218793_det1.jpg` | 0.0096 | 0.442 (low-contrast product + high-contrast shadow — genuinely competes for saliency) |
  | `graphite-scarf.jpg` | 0.0120 | 0.723 |
  | `2426834-7558_bottom-packshot_sole.jpg` | 0.0144 | 0.780 |
  | `OMB-E166-BV_1.jpg` | 0.0360 | 0.424 (near-equal shadow/subject saliency strength) |
  | `2426834-7558_top-packshot_overhead.jpg` | 0.0407 | 0.763 |
  | `OMB-E129-TGV_3.jpg` | no measurement — KO'd `MATCH_NOT_FOUND` at matching, never reached Transform/Subject stage (expected, unrelated to shadows) |

  Value has since
  moved 0.05 → 0.0082 → 0.001 → 0.042 while searching for a better number. At **0.0082** a real side
  effect appeared: `2426834-7558_top-packshot_overhead.jpg`'s bounding box got trimmed by the shadow-strip
  logic from 591px to 556px height, crossing the 570px minimum-size floor and KO'ing (`PREPROCESS_TOO_SMALL`)
  an image that passes at other values — confirmed deterministic across 5 repeated runs at 0.0082 (identical
  box every time: `X=129,Y=214,W=460,H=591` pre-trim). At **0.042** the same image no longer KOs
  (`HasHardShadowEvidence` stays false since 0.0407 < 0.042) and reaches the transform stage normally.
  The user intends to refine the shadow detector itself later, which will shift this whole distribution —
  treat any threshold chosen now as provisional.
- Centering A/B. [[T-4850]] asked that the promoted subject box show "equal-or-better centering" than
  the legacy salient box. Measured over 71 promoted images: close agreement on the bulk (centre-shift
  median 15.5px on ~3500px images, 51/71 within 50px, area-ratio median 1.027), but a tail of ~20
  disagreements clustered at mid confidence (0.48–0.61) where geometry alone can't say which box is
  *better* centred — needs the tail eyeballed (port `save_debug_overlay` from the reference prototype)
  or scored against labelled product bounds. Related and minor: SPACINI29 is entirely `SOLIDCOLOR`, so
  the B2 `HeroDetectionOnSteroids` real-life-background path has never run against real data — needs a
  real-life-background dataset whenever this sub-item gets picked up.

**Decision(s):**
- What should `HardShadowEvidenceFraction` actually be? Currently `0.042` in `ClassifyConfig.json:69`
  (inline comment still reads `0.0082` — update once this is locked in). Not yet confirmed final: must
  clear all 5 labelled-hard CiMini measurements (0.0096–0.0407) without reproducing the old 0.01/0.0082
  failure mode (SPACINI29's own measured minimum is 0.0113 — anything below that risks firing on
  everything again) and without KO'ing images that should pass (the `top-packshot_overhead.jpg`
  regression seen at 0.0082).

**Test(s):**
- A/B test on a throwaway evidence harness: run the 6-image labelled-hard sample *and* a sample of
  ordinary (non-hard-shadow) CiMini/SPACINI29 images at the candidate threshold, compare
  `HardShadowStrippedFraction`/`HasHardShadowEvidence` across both groups. This is the false-positive
  check flagged when 0.0082 was set and never run — still open.
- Full CI unit test suite (`dotnet test jb/src/PRISM.sln -m:1`) once a threshold is chosen, to confirm
  the change doesn't reproduce the `top-packshot_overhead.jpg`-style regression elsewhere in CiMini.

**Update 2026-08-26 — false-positive check run, negative result: the metric doesn't discriminate at
any threshold.** Ran the A/B harness (`.claude/skills/prism-evidence-report/harness/EvidenceDumpHarness.cs`,
`transform` section) over all of CiMini + SPACINI29 at the currently-shipped 0.042. 158 non-KO images
carried a measurement; 5 of the 6 labelled-hard images were present (`OMB-E129-TGV_3.jpg` still KO's at
matching before reaching Subject detection, as already documented above — unrelated to shadows). All 5
labelled-hard images sit at 0.0096–0.0407, same range already on record.

The 153 **ordinary** (non-labelled) images measured: min 0.0000, median **0.0381**, p90 0.0657, max
0.1343 — split evenly by dataset (CiMini n=67 median 0.0398; SPACINI29 n=86 median 0.0380, comparable
shape in both). **59 of 153 (38.6%) cross 0.042** — nearly 4 in 10 ordinary images register as
hard-shadow at the currently-shipped value. Worked examples: `AY_FFK0230_83035_03FW001_c.png` (0.1343),
both `triggered_black-tshirt-*-americain.jpg` (~0.125), `grey-scarf.jpg` (0.0924), several SPACINI29
studio shots in the 0.06–0.08 range.

**This isn't a "threshold slightly off" result — the two populations are not separable by this metric at
any threshold.** The ordinary-image median (0.0381) sits almost exactly at the candidate value, and the
ordinary distribution's full range (0.0000–0.1343) contains the entire labelled-hard range (0.0096–0.0407)
with heavy overlap, not just a few outliers. Raising the threshold high enough to exclude most ordinary
images (past the 0.0657 p90, say) would also exclude every one of the 5 labelled-hard images, whose max is
0.0407 — there is no value that both fires on real hard shadows and stays quiet on ordinary texture. No
threshold change fixes this; it's the measurement itself (`SubjectDetector`'s texture-vs-chroma strip
fraction) that doesn't separate the two cases on the current data. Matches the ticket's own standing
caveat that the shadow detector will need refining before a threshold here means anything durable — this
result is the confirmation of that, not a surprise on top of it.

**Recommendation, not yet actioned:** don't lock in 0.042 (or hunt for a nearby replacement — the false-
positive sweep above shows no nearby value works either). Leave `HardShadowEvidenceFraction` as-is and
mark this half of the ticket blocked on a `SubjectDetector` measurement change (the texture/chroma
separation the fraction is computed from), not a config tune. Full CI run (second Test(s) bullet) not yet
re-run against this finding, since no new value is being proposed.
