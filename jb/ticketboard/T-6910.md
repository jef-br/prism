### T-6910 · Full-resolution pixel analysis runs twice per image, and the second pass is single-threaded
**Status:** Review | **Profile:** P1-feature-worker

> **Direction 1 implemented 2026-08-11** (user-authorised: "if small, do now"). `RefinePhenotypes` now
> runs `Parallel.ForEach` over the batch with `Interlocked` counters, reusing the same `ParallelOptions`
> the Analyze loop already uses. **Direction 2 (scaled decode) is deliberately NOT done** — it changes
> measured values and needs the golden re-blessed; it remains this ticket's open work.
>
> **Thread-safety was verified before writing the change, not assumed:** all 12 `Analyzer_*` types are
> `static` with no fields; `ImageFeatureAnalyzer` holds no static mutable state; `SubjectDetector`,
> `ProductTypeResolver` and `PhenotypeRuleSet` expose only `readonly` config after construction;
> `YoloDetector.Detect` serializes on its own `RunLock`; `familyById` is fully built before the loop.
> Each iteration writes only to its own lambda, so the result is order-independent.
>
> **Verification:** build 0 errors / 0 warnings · `Prism.Services.Matching.Tests` 275/275 (273 + 2 new)
> · `Prism.Core.Tests` 151/153, the same 2 CiMini KNOWN-RED failures as before the change, no new ones
> · new `RefinePhenotypesParallelTests` pins the two properties a regression would break first (counter
> increments not lost to a race; two runs produce identical per-image phenotypes) over 40 real images,
> sized so `Parallel.ForEach` actually uses multiple threads.
**Found by:** [[T-6900]] root-cause measurement, 2026-08-11. Split out because it is a throughput
defect in its own right, independent of that ticket's "is it hanging?" question.

**The problem.** Every image in a job is decoded at full resolution and analysed per-pixel **twice**:

1. **`MatchingService.PrepareLambda`** → `ImageFeatureAnalyzer.Analyze` — runs inside the chunked
   `Parallel.For` (`MatchingService.cs:83`), so it uses up to 8 threads
   (`MaxDegreeOfParallelism = Math.Min(ProcessorCount, 8)`).
2. **`MatchingService.RefinePhenotypes`** → `ImageFeatureAnalyzer.Refine` — **re-reads the image from
   disk** (`ImageFeatureAnalyzer.cs:120`, `Image.Load<Rgba32>(imagePath)`) and runs YOLO, subject
   geometry, dominant colours, background colour, exposure and subject isolation over it. This is a
   plain sequential `foreach` (`MatchingService.cs:313`) — **one thread, no parallelism at all**.

**Both passes are now measured** on real SMASHEDLEMON45 images (1774 images, 13,130 MP total):

| Pass | Avg/image | Total CPU | Parallelism | **Wall clock** |
|---|---|---|---|---|
| 1 — `Analyze` | 2609 ms | **77.1 min** | 8 threads | **≈9.6 min** |
| 2 — `Refine` | 750 ms | **22.2 min** | **1 thread** | **≈22.2 min** |

**This is the headline: pass 2 is 22% of the CPU work but roughly two-thirds of the wall clock**,
purely because it never got a `Parallel.For`. Predicted total ≈35-40 min, which matches the original
45-minute observation in [[T-5200]].

Pass 2 is also much cheaper per pixel than pass 1 (750 ms vs 2609 ms average) because YOLO resizes to
a fixed input — so its cost is far less resolution-driven. **Parallelizing pass 2 is therefore both the
cheapest fix and the biggest single wall-clock win available in the pipeline.**

### The two passes are distinguishable live, which makes progress diagnosable
`ImageMatcher.RunWaterfall` emits no SSE progress, so the Match stage is a black box — but the two
passes have clearly different process signatures, sampled on the running job:

| Phase | Cores | Working set |
|---|---|---|
| Pass 1 (`Analyze`, chunked parallel) | **3.0** | ~1430 MB (8 decoded images held per chunk) |
| Pass 2 (`Refine`, sequential) | **1.37** | ~926 MB (one image at a time) |

A `Get-Process Prism.Api` CPU-delta sample therefore tells you which pass a stuck-looking job is in.
Worth knowing before anyone again reads sustained CPU as evidence of a hang, as [[T-5200]] did.

### Third finding: pass 1 only achieves ~3 of its 8 nominal threads
Live measurement of the running job (`Get-Process Prism.Api`, CPU delta over wall clock) shows a
**sustained 3.0 cores**, not the 8 that `MaxDegreeOfParallelism` allows. Cause: the loop is chunked at
`ClipChunkSize = 8` and `Parallel.For` runs *within* a chunk, so **every 8 images is a barrier**. This
dataset mixes 1.4 MP and 18.8 MP images whose analyze cost differs **13×** (422 ms vs 5514 ms), so
seven threads sit idle waiting for the one 18.8 MP image in their chunk before the next chunk starts.

Effective parallelism is therefore driven by the *cost variance within each chunk*, not by the thread
cap. Fixing this needs either a flat `Parallel.ForEach` over all images with chunking only for the CLIP
batch, or size-aware chunk packing. Note the chunk size exists to bound how many decoded images are
held in memory for the batched CLIP `Run` — any restructure has to preserve that bound (8 × 18.8 MP ×
4 bytes ≈ 600 MB today).

**Why this matters beyond one dataset.** Documented batch cap is 10,000 images
(`Input.Images.amount.max`). At SMASHEDLEMON45's average image size that is a multi-hour job dominated
by a single-threaded loop while 19 of 20 cores idle.

**Two independent directions, weigh both:**
1. **Parallelize `RefinePhenotypes`.** Cheapest change, no behavioural risk to what is measured.
   Caveats: `YoloDetector.Detect` already serializes on its own `RunLock`
   (`YoloDetector.cs:90`), so YOLO inference will not speed up — only the decode and the
   per-pixel analyzers will. Thread-safety of each `Analyzer_*` must be confirmed, not assumed;
   `PhenotypePool` is constructed per call so it is already fine.
2. **Stop decoding at full resolution.** The analyzers measure composition, geometry, colour
   distribution and exposure — all scale-invariant. Decoding an 18.8 MP garment shot to measure
   `product-coverage-ratio` is waste; ImageSharp's JPEG decoder supports scaled decode. **This changes
   measured values and therefore phenotypes, so it needs the CiMini golden re-scored and cannot be done
   silently** — that is why it is a separate direction, not a bolt-on to #1.

**Also worth deciding here:** pass 1 runs even when `SkipClassification=true`. The `doClassify` gate
skips CLIP but not decode/hash/feature-analysis, so a match-only run spends ~64 CPU-minutes on
measurements matching never reads. A match-only fast path is a third, orthogonal option.

**Measurement tooling already exists** — `TempPrematchTimingHarness.cs` in the Matching test project
times decode/hash/analyze/refine per image on any folder, no-op unless `PRISM_TIMING_DIR` is set. Reuse
it to confirm any fix rather than re-deriving the numbers.
