### T-5140 · Tx_ProblemImageProcessor reports pre-upscale output metadata
**Status:** Ready | **Profile:** P1-feature-worker
**Found by:** [[T-5010]] review, 2026-07-31; split out as a separate issue 2026-08-12

`Tx_ProblemImageProcessor.Transform` (`Tx_ProblemImageProcessor.cs:50`) computes
`OutputRecord.OutputWidth`/`OutputHeight`/`ScaleFactor` via `ComputeSafeResizeTarget(InputImage.Width,
InputImage.Height, ...)` — the pre-upscale dimensions. `ImagePreProcessor.ScaleGeometryToUpscaledImage`
deliberately never updates `lambda.Width`/`.Height` (they are the original-resolution contract the
upscale manifest reports against), so when an image on this route gets upscaled, `ProcessedBytes`
reflects the upscaled size while `OutputWidth`/`OutputHeight`/`ScaleFactor` in the manifest still report
the original pre-upscale numbers. **Effect:** manifest metadata is wrong (reports smaller dimensions /
`ScaleFactor` 1.0) for any image that both routes to `Tx_ProblemImageProcessor` and gets upscaled.

Originally raised in [[T-5010]] as one of two "dormant sizing defects." That ticket has since removed
the phenotype/det-slot gate from `ImageTransformer.SelectTransformer` entirely (2026-08-11 DetailCropper
rework), so blast radius on SPACINI29 shrank a lot — `Tx_ProblemImageProcessor` is now reached only when
`BoundingBox` is null, not on ~57/86 images as originally measured. Still a live, unfixed defect for
whatever does reach that path (e.g. failed subject detection). **Re-measure blast radius against current
routing before fixing** — do not reuse the old 57/86 figure, it predates the gate removal.
