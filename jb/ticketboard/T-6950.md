### T-6950 · Direction 2: stop decoding at full resolution for scale-invariant analyzers
**Status:** Ready | **Profile:** P1-feature-worker
**Found by:** [[T-6910]], 2026-08-11 — deliberately not done in that ticket; split out so the decision and the re-bless work stay tracked rather than sitting undecided in the archive.

The feature analyzers are scale-invariant, so decoding images at full resolution just to measure them is wasted work — but changing the decode scale changes measured values and downstream phenotype outputs, so it can't be done silently. Split out from T-6910, where it was deliberately left undone, so the decision and re-bless work stay tracked.

**Problem(s):**
- The feature analyzers measure composition, geometry, colour distribution and exposure — all scale-invariant. Decoding an 18.8 MP garment shot at full resolution to measure `product-coverage-ratio` is waste; ImageSharp's JPEG decoder supports scaled decode.

**Decision(s):**
- Trade-off (from T-6910's review): taking this on buys further wall-clock savings on top of T-6910's parallelization fix, at the cost of a one-time re-bless-and-validate pass on the CiMini golden. Whether that trade is worth it now is a product call, not decided here — record the decision and its reasoning in `jb/docs/PRISM-match.md` or the relevant analyzer doc either way, once made.
- If taken on, still need to pick a scaled-decode target size per analyzer (or one shared target) — not decided here.

**Test(s):**
- If taken on: measure the wall-clock win on SMASHEDLEMON45-scale data with the chosen scaled-decode size(s), and re-capture the CiMini golden's phenotype assignments at the new decode values (`test/datasets/CiMini/expected-phenotype.json`) for the review below.

**Reviewer(s):**
- A human must review the re-captured CiMini golden's new phenotype assignments and confirm they're still correct — not just different — before re-blessing; this can't be automated or done silently since scaling the decode changes the actual measured pixel values feeding the analyzers, which changes phenotype outputs on some images. This is why the work doesn't fold into T-6910's parallelization fix as a bolt-on.

**Files:** `jb/src/core/Services/Matching/Classify/ImageFeatureAnalyzer.cs`, the `Analyzer_*` chain consumers of decoded image data, `test/datasets/CiMini/expected-phenotype.json` (golden, needs re-bless), `jb/docs/PRISM-match.md` (or the relevant analyzer doc, for recording the decision).
