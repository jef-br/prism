### T-5120 · Filename and folder tokens should contribute to phenotyping, matching and ordering
**Status:** Blocked | **Profile:** P4-critical-architecture
**Raised by:** user direction, 2026-08-07, while specifying the overflow-to-the-end rule ([[T-5060]] successor).

Every signal PRISM extracts about an image is a token, and tokens live in one of four bags: numeric
(`98765432`, `_2`, `76`, EAN-like runs, shot numbers), string (`front`, `DETAIL`, `packshots`, `Cedric`,
folder segments, Excel cell text), clip (`hero-orientation=BACK 0.40`, `hero-is-human=TRUE 0.97`,
phenotype candidates), and analyzer (YOLO boxes, edge intersections, `salient-bbox`, occupancy,
dominant colours). All four bags should be able to contribute to matching, ordering, and phenotyping —
today they're siloed (see Problem(s) below). This is a cross-cutting change to four pipeline stages.

**Gate — do not start work until all of these hold:** the repo is clean, up to date and synced with
origin; the last CI run was green; the agent session memory is still empty (fresh session, no
accumulated context); and the current session window — accounting for the 5-hour rolling window and
tokens already spent — is comfortably roomy. The change must land in one uninterrupted pass, not
squeezed into the tail of a session.

**Problem(s):**
- The four token bags are siloed instead of jointly informing matching, ordering, and phenotyping.
  Filename tokens reach matching (`StringMatcher`, `FilenameToCellMatcher`, `SubstringRescue`) and
  reach ordering only as a tie-break (`DetOrderConfig.FilenameMatchesSlotKeyword`), while phenotyping
  reads only the clip and analyzer bags. Effect: a `*_DETAIL.jpg` in a `details/` folder gets no
  phenotype at all if CLIP fails to classify it, even though two independent string tokens already say
  "detail". Fix direction: a filename/folder token should become weak evidence able to produce or
  promote a `SelectedPhenotype`; when multiple images then qualify for one slot, the image with the
  strongest *total* signal across all four bags wins — `ImageOrderer.CompareCandidates` already ranks
  candidates this way, what it lacks is a way to weigh a string token against a CLIP confidence — and a
  genuine tie goes to first-past-the-post. Related tickets to read first, since this ticket may subsume
  or reshape them: [[T-5090]] (SubstringRescue invents evidence from shot numbers) and [[T-5110]]
  (filename-in-cell never fires), both numeric/string-bag problems; [[T-5080]] and [[T-2840]] cover the
  clip bag's reliability, which caps how much weight the clip bag deserves relative to the string bag.

**Decision(s):**
- Filename tokenization scope — decided and landed 2026-08-07: `FilenameMatchesSlotKeyword` now
  tokenizes the whole of `InitialFullName`, folder segments included, splitting on `/ \ _ - space .`,
  instead of taking only the leaf basename. So `A/temp/images/detail/98765432/1.jpg` now produces the
  token `detail`. The path data was always there — ZIP/folder ingress preserve it (`ZipExtractedMember`,
  `PipelineFixture`) — it was being discarded by a single `Path.GetFileNameWithoutExtension` call. This
  is the prerequisite the rest of this ticket builds on.
- Sequence tokens in scope, and work through det order — decided (user direction, 2026-08-07): a
  trailing suffix like `_2`, `_B`, `_F1`, `-03` is weak *positional* evidence, not content evidence.
  `DetOrderRules.json` already maps position → phenotype per product type, so the chain is: sequence
  token → likely det slot → that slot's phenotype list → weak prior on those phenotypes; an independent
  signal pointing the same way earns a bonus. Worked example: `SHIRT_RED_2.jpg`, product type
  `topwear` — the `_2` suffix suggests the second det slot, and `topwear.det1` lists
  `back-on-model-partial`, `back-on-model-full-product`, `back-packshot` (all "back"); CLIP
  independently reads `hero-orientation = BACK` at 0.35, too weak alone to trust, but the two unrelated
  bags agreeing clears the bar neither cleared alone. Counter-example (the guard rail): same file, but
  CLIP reads `hero-orientation = FRONT` at 0.52 with `hero-is-human = TRUE` at 0.97 — the signals
  disagree and the measured one is far stronger, so the `_2` prior must lose outright. The prior is only
  allowed to break ties and lift near-misses, never to overturn confident measured evidence — a
  photographer who shoots back-first breaks the convention, and the system has to survive that.
- Does `_1` mean det0 or det1? — open, decide before implementing. Customer numbering is usually
  1-based, so `_1` → det0 is the likely reading, but guessing this inverts every family that uses it.
  Measure it on `test/datasets` before choosing.
- Plurals don't match the keyword stems — open. Matching is exact against `DetOrderKeywordStems.json`
  (`stems.Contains(token)`). The user's own example folders, `packshots/` and `details/`, match
  *nothing*, because the stems are `pack` and `detail`, singular. Either add plural forms to the stems
  config (config-driven, consistent with "no magic values inline", but doubles the config surface) or
  move to prefix/stem matching.
- `pack`/`packshot` keyword collision — open, and dangerous. The `pack` keyword in `DetOrderRules.json`
  means *packaging* — a box, `det6`, stems `pack`/`package`/`box`/`boite`/`caja`/`verpackung`. A folder
  named `packshots/` means the opposite: plain product shots on white, which belong at `det0`-ish, not
  the packaging slot. Cause: one keyword string serving two unrelated concepts. Effect: naively adding
  `packshots` to the `pack` stem list would route every product shot in that folder to the packaging
  slot. Consequence: the catalogue leads with the wrong image for every family in that folder. Must
  resolve this collision explicitly — probably by renaming the packaging keyword — before any plural or
  prefix matching is switched on.
- Token-derived phenotype visibility — open, also in scope: decide whether a token-derived phenotype
  should be visible to `ImageMatcher.HasDuplicatePhenotypeInFamily` (it rejects a match when the family
  already holds that phenotype — a wrong token-derived phenotype would start rejecting valid matches)
  and to `ImageTransformer`'s `SelectedPhenotype is null` routing (a token-derived phenotype would pull
  images out of `Tx_ProblemImageProcessor` and into normal geometry routes). Both are behaviour changes
  well outside ordering.

**Test(s):**
- Acceptance: a `*_DETAIL.jpg` with no CLIP phenotype (see Problem(s) above) must land in the detail
  slot rather than the overflow tail.
- Acceptance: the `pack`/`packshot` collision (see Decision(s) above) must be resolved with no product
  shot routed to the packaging slot.
- Ready-made before/after acceptance case, found 2026-08-11 while fixing [[T-5100]]: once
  `OMB-E180-BV_*` correctly stopped being misassigned to family `98636303`, that family's real images
  (`OMB-E166-BV_1..4.jpg`) came out reordered by the current overflow logic — filename suffix order is
  `_1,_2,_3,_4`, but det-slot assignment doesn't track it: `_1→det1, _2→det2, _3→det3, _4→det0` in the
  live run. Desired order per user direction: for a `_1.._N` filename family, the order should be
  `0,1,2,...,N-1` matching the suffix directly; `_1..._4` may reasonably shuffle among each other given
  visual similarity between those specific images, but the assignment must not be arbitrary beyond that
  (`_4` landing at `det0`, ahead of `_1`, is not acceptable). `expected-manifest.json` was deliberately
  **not** re-blessed for this family's DetOrder/FinalFileName fields — matching (FamilyId) was
  re-blessed since T-5100 fixed a real defect there, but the ordering itself needs this ticket's fix,
  not a captured snapshot of today's wrong order. When this ticket starts, treat `OMB-E166-BV_1..4` as
  this ready-made case, and re-capture CiMini's golden deliberately with the new expectations recorded
  — not silently re-blessed.
