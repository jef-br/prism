### T-5120 · Filename and folder tokens should contribute to phenotyping, matching and ordering
**Status:** Blocked | **Profile:** P4-critical-architecture
**Raised by:** user direction, 2026-08-07, while specifying the overflow-to-the-end rule ([[T-5060]] successor).

**Handling constraint — this ticket is deliberately gated.** Do not start work unless *all* of the
following hold: the repo is clean, up to date and synced with origin; the last CI run was green; the
agent session memory is still empty (fresh session, no accumulated context); and the current session
window — accounting for the 5-hour rolling window and tokens already spent — is comfortably roomy.
This is a cross-cutting change to four pipeline stages and must be done in one uninterrupted pass, not
squeezed into the tail of a session.

**The idea.** Every signal PRISM extracts about an image is a token, and tokens live in a bag of four
bags:

| Bag | Examples |
|---|---|
| numeric | `98765432`, `_2`, `76`, EAN-like runs, shot numbers |
| string | `front`, `DETAIL`, `packshots`, `Cedric`, folder segments, Excel cell text |
| clip | `hero-orientation=BACK 0.40`, `hero-is-human=TRUE 0.97`, phenotype candidates |
| analyzer | YOLO boxes, edge intersections, `salient-bbox`, occupancy, dominant colours |

**All four bags can contribute to matching, ordering, and phenotyping.** Today they are siloed:
filename tokens reach matching (`StringMatcher`, `FilenameToCellMatcher`, `SubstringRescue`) and reach
ordering only as a tie-break (`DetOrderConfig.FilenameMatchesSlotKeyword`), while phenotyping reads
clip + analyzer bags exclusively. A `*_DETAIL.jpg` in a `details/` folder currently yields no phenotype
at all if CLIP fails to classify it, even though two independent string tokens say "detail".

**Concretely, what changes:** a filename or folder token becomes weak evidence that can produce or
promote a `SelectedPhenotype`. Multiple images may then qualify for one slot — the image with the
strongest *total* signal across all four bags wins, and on a genuine tie the first past the post takes
it. That ranking already exists in `ImageOrderer.CompareCandidates`; what it lacks is a way to weigh a
string token against a CLIP confidence.

**Sequence tokens are in scope, and they work through det order (user direction, 2026-08-07).** A
trailing `_2`, `_B`, `_F1`, `-03` is a weak signal too. It says nothing about image *content*, but it
says something about *position*, and `DetOrderRules.json` already maps position → phenotype for each
product type. So the chain runs: sequence token → likely det slot → that slot's phenotype list → weak
prior on those phenotypes. When an independent signal points the same way, the agreement earns a bonus.

Worked example. `SHIRT_RED_2.jpg`, product type `topwear`. The `_2` suffix suggests the second det
slot, and `topwear.det1` lists `back-on-model-partial`, `back-on-model-full-product`, `back-packshot`
— all "back". CLIP independently reads `hero-orientation = BACK` at 0.35, on its own too weak to
trust. Two unrelated bags agree on "back", so the combination clears the bar that neither cleared
alone.

Counter-example, and this is the guard rail. Same file, but CLIP reads `hero-orientation = FRONT` at
0.52 with `hero-is-human = TRUE` at 0.97. The signals disagree, and the measured one is far stronger.
The `_2` prior must lose outright — it is allowed to break ties and lift near-misses, never to
overturn confident measured evidence. A photographer who shoots back-first breaks the convention, and
the system has to survive that.

**Decide before implementing:** whether `_1` means det0 or det1. Customer numbering is usually
1-based, so `_1` → det0 is the likely reading, but guessing this inverts every family that uses it.
Measure it on `test/datasets` before choosing.

**Prerequisite already landed (2026-08-07):** `FilenameMatchesSlotKeyword` now tokenizes the whole of
`InitialFullName`, folder segments included, splitting on `/ \ _ - space .` instead of taking the leaf
basename. So `A/temp/images/detail/98765432/1.jpg` already produces the token `detail`. The path data
was always there — ZIP and folder ingress preserve it (`ZipExtractedMember`, `PipelineFixture`) — it
was being discarded by a single `Path.GetFileNameWithoutExtension` call.

**Two traps found while landing that prerequisite. Both need a decision before this ticket proceeds.**

1. **Plurals do not match.** Matching is exact against `DetOrderKeywordStems.json`
   (`stems.Contains(token)`). The user's own example folders — `packshots/` and `details/` — match
   *nothing*: the stems are `pack` and `detail`, singular. Either add plural forms to the stems config
   or move to prefix/stem matching. Adding plurals is the config-driven option and stays consistent
   with "no magic values inline", but it doubles the config surface.

2. **`packshots` is a false friend, and this one is dangerous.** The `pack` keyword in
   `DetOrderRules.json` means *packaging* — a box, `det6`, stems `pack`/`package`/`box`/`boite`/
   `caja`/`verpackung`. A folder named `packshots/` means the opposite: plain product shots on white,
   which belong at `det0`-ish, not in the packaging slot. Naively adding `packshots` to the `pack`
   stem list would route every product shot in that folder to the packaging slot. **Cause:** one
   keyword string serving two unrelated concepts. **Effect:** a whole folder of main product images
   lands in the packaging det slot. **Consequence:** the catalogue leads with the wrong image for
   every family in that folder. Resolve the `pack`/`packshot` collision explicitly — probably by
   renaming the packaging keyword — before any plural or prefix matching is switched on.

**Also in scope:** decide whether a token-derived phenotype should be visible to
`ImageMatcher.HasDuplicatePhenotypeInFamily` (it rejects a match when the family already holds that
phenotype — a wrong token-derived phenotype would start rejecting valid matches) and to
`ImageTransformer`'s `SelectedPhenotype is null` routing (a token-derived phenotype would pull images
out of `Tx_ProblemImageProcessor` and into normal geometry routes). Both are behaviour changes well
outside ordering.

**Related:** [[T-5090]] (SubstringRescue invents evidence from shot numbers) and [[T-5110]]
(filename-in-cell never fires) are both numeric/string-bag problems and should be read before starting
— this ticket may subsume or reshape them. [[T-5080]] and [[T-2840]] cover the clip bag's reliability,
which sets a ceiling on how much weight the clip bag deserves relative to the string bag.

**Acceptance:** a `*_DETAIL.jpg` with no CLIP phenotype lands in the detail slot rather than the
overflow tail; the `pack`/`packshot` collision is resolved with no product shot routed to the
packaging slot; CiMini's golden is re-captured deliberately with the new expectations recorded, not
silently re-blessed.
