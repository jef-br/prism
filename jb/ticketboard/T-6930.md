### T-6930 · Pass 1's chunk barrier caps effective parallelism at ~3 of 8 threads
**Status:** Ready | **Profile:** P1-feature-worker
**Found by:** [[T-6910]], 2026-08-11 — third finding, split out on close so it isn't lost in the archive.

Pass 1's chunked `Parallel.For` creates a synchronization barrier every 8 images, capping effective parallelism far below the configured thread count on datasets with mixed image sizes. Split out from T-6910 on close so the finding isn't lost in the archive.

**Problem(s):**
- `MatchingService`'s `Analyze` loop (`MatchingService.cs`, chunked `Parallel.For` around line ~79) chunks at `ClipChunkSize = 8` and runs `Parallel.For` *within* each chunk, so every 8 images is a synchronization barrier. The dataset mixes 1.4 MP and 18.8 MP images whose per-image analyze cost differs 13× (422 ms vs 5514 ms), so seven threads sit idle waiting for the one 18.8 MP image in their chunk before the next chunk's barrier releases. Live measurement on a running SMASHEDLEMON45 job (`Get-Process Prism.Api`, CPU delta over wall clock) showed a sustained 3.0 cores, not the 8 threads `MaxDegreeOfParallelism` allows.
- Documented batch cap is 10,000 images (`Input.Images.amount.max`). On a batch with this kind of size variance, this turns into a multi-hour job dominated by idle cores, not compute.

**Decision(s):**
- Shape of the fix is undecided (from T-6910, not settled here): either a flat `Parallel.ForEach` over all images with chunking applied only to the CLIP batch call, or size-aware chunk packing (bin images by estimated cost rather than arrival order). The chunk size exists to bound how many decoded images are held in memory for the batched CLIP `Run` (8 × 18.8 MP × 4 bytes ≈ 600 MB today) — any restructure has to preserve that bound.

**Test(s):**
- Acceptance: re-measure sustained core utilization on the same SMASHEDLEMON45 job after the fix (baseline of 3.0 sustained cores already captured, see Problem above) and report the wall-clock change; confirm the CLIP batch memory bound is preserved; confirm no CiMini golden regression.

**Files:** `jb/src/core/Services/Matching/MatchingService.cs` (`PrepareLambda`/chunked loop, `ClipChunkSize`).
