### T-6920 · Unique-article match should still refuse a colour code the family's Excel data doesn't have
**Status:** Ready | **Profile:** P1-feature-worker — requires `/pair` (judgment-heavy matching logic,
per repo convention)
**Found by:** [[T-6900]], 2026-08-11 — the SMASHEDLEMON45 measurement's one open product question, now
decided.

Article `26316` has exactly one Excel row, `26316-520`. Bracket 1 (`NumericMatcher`) matches any image
whose article number is unique in the catalogue, regardless of whether the filename's colour token
agrees with the row it's matching to. Confirmed on live data: `26316_520_*` (7 images) correctly matches
`99985091`; `26316_000_*` (7 images) *also* matches `99985091`, even though colour `000` has no Excel
row anywhere under article `26316`.

**Decision (user, 2026-08-11, verified against the full 14-image `26316_*` set and the Excel row):**
a contradicting colour token must veto a unique-article match. `26316_520*` → matches `99985091`.
`26316_000*` → must be refused (`MATCH_NOT_FOUND` or a new KO reason), not force-matched.

**The check is per-family colour-code membership, not a global colour dictionary.** Don't build a
code→colour-name table (e.g. "520 = green") — that's unnecessary generalization for this case and a
bigger, fuzzier project. Instead: when Bracket 1 is about to accept a unique-article match, confirm the
filename's colour code appears among *that family's own* Excel rows (the set of colour codes on rows
sharing the matched article). If it doesn't, refuse the match instead of accepting it on article
uniqueness alone.

**Why this needs `/pair`:** this changes Bracket 1 acceptance criteria in `NumericMatcher` — matching
correctness code, per this repo's convention that judgment-heavy matching/scoring changes are worked
through Socratic pairing, not solo-implemented.

**Watch for:** articles that are unique in the catalogue specifically *because* they only have one
colour row — for those, the filename colour code should still agree with that one row; don't
accidentally require a match against a *set* of codes when the family truly only has one. Also check
this doesn't regress the 587 Bracket-2-resolved images that already handle multi-colour articles via
token concatenation — this is a Bracket 1 change, so verify Bracket 2's path is unaffected.

**Acceptance:** `26316_520_*` still resolves to `99985091`; `26316_000_*` becomes `MATCH_NOT_FOUND` (or
an equivalent explicit KO, not a silent drop); SMASHEDLEMON45's fast harness
(`TempSmashedLemonMatchHarness.cs`, kept per [[T-6900]]) re-run shows 0 wrong matches and the new KO
accounted for; full Matching test suite green; no CiMini golden regression.
