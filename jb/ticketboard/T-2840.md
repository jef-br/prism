### T-2840 · CLIP classification differs by submission transport for near-tied confidence scores
**Status:** Ready | **Profile:** P4-critical-architecture
**Found by:** widening `PipelineFixture` to submit the full CiMini dataset, 2026-08-06 — see
`test/datasets/CiMini/README.md` history note and [[T-4980]]/[[T-5060]]'s update notes for the merge
context.

**This is [[T-2820]] recurring under a angle T-2820 never tested.** T-2820 ("Ordered stage assigns
non-deterministic det-slots for tied images") was closed 2026-07-15 as not-reproducing: 3-5 consecutive
`Invoke-CiPipeline.ps1 -Mode Full -Dataset CiMini` runs (same transport, same process) gave
byte-identical output every time. **That is still true — confirmed again below — but T-2820 never
compared two *different* submission transports against each other for the same logical input.** This
ticket does, and they disagree.

**Evidence.** `CiMiniGoldenTests.CiMini_Manifest_MatchesCommittedGolden` (`dotnet test`, via
`PipelineFixture` — a direct in-process `PrismService.Process()` call submitting every image loose)
mismatches the golden captured by `Invoke-CiPipeline.ps1 -Mode Full -Capture` (a real HTTP job — its
`Submit-PrismJob` sends exactly one seed image via multipart and repacks *every other image*, including
plain top-level loose files, into a synthetic zip uploaded as a second multipart part) on exactly 4
families beyond the already-known Pareo/94613033 case ([[T-5080]]): `99985047`
(`26182-Denim-801/a (1).jpg` vs `87186790_2.jpg`), `99147525` (3 `C153KB460011_*.png` files), and
`98636303` (`OMB-E180-BV_1/2/3.jpg`).

- Confirmed fully deterministic *within* the `PipelineFixture` transport: 3 repeated `dotnet test` runs
  (separate processes) gave byte-identical mismatches every time. Matches T-2820's own same-transport
  finding — the non-determinism is not random/GPU-jitter-flaky.
- Read `ImageOrderer.ProcessFamily`: overflow ordering sorts purely by `Anchor → OnModelRank →
  InitialFullName (natural comparer) → Index` — filename-content-based, not list-position-based. Read
  `Importer.SortDeterministically` (T-2820's own fix) and `MatchingService.MatchAsync`'s indexed
  `results[chunkStart+i]` writes: input order is explicitly normalized to `InitialFullName`-sorted and
  preserved through classification regardless of submission order. So transport-level ordering cannot
  explain this by itself — the *tie-break logic* is not the bug.
- Used the evidence-dump harness (`.claude/skills/prism-evidence-report/harness/EvidenceDumpHarness.cs`
  — copy into `jb/src/tests/Prism.Core.Tests/`, run, delete after) to inspect family `98636303`:
  `OMB-E180-BV_1.jpg` and `_3.jpg` both resolve to the single candidate phenotype `back-packshot`, both
  `hero-orientation=BACK`, confidence **0.39 vs 0.40** — a near-tie sitting barely above the
  already-documented-fragile 0.33 threshold (`test/datasets/CiMini/README.md`'s "Filename keywords will
  silently decide the answer" section; [[T-5080]]). In the `PipelineFixture` transport `_1` wins the
  slot (deterministic filename-ordinal tie-break, given that candidate set); the ps1-captured golden has
  `_3` winning instead — meaning the *candidate set itself* differed between transports, i.e. actual
  classification output differed for at least one image per affected family.
- Checked whether `ImageSourceKind` (`ZipMember` vs `LocalPath` — the two transports produce different
  values for the same logical image) is consumed anywhere in `Services/Matching`: it is not referenced
  at all, so it is not a direct behavioral switch. The mechanism is still open.

**User direction on T-2820, still the best lead (2026-07-14):** *"the fix likely lives in CLIP
refinement, not in a tie-break hack. If two images in a family score near-identically, that is the
classifier failing to distinguish them."* Confidence values this close (0.39/0.40, both barely clearing
0.33) are exactly that case. A deterministic secondary tie-break (which is what already exists and is
working correctly) only freezes an arbitrary winner in place — it doesn't fix a classifier that can't
tell two images apart.

**Step 1 CONFIRMED, 2026-08-11 — batch-composition sensitivity is real.** Isolated-batch experiment
run: family `98636303` (`OMB-E180-BV_1..6.jpg`) submitted alone in a scratch `test/datasets/` folder
(full `Brackets-Complete.xlsx` included, so only the image-batch composition variable changed — not
matching context) via the evidence harness, `hero-orientation` confidence diffed against the same
images' values from a fresh full-CiMini run in the same session (same transport, `PipelineFixture`
both times — this isolates batch composition specifically, independent of the
transport/ZIP-vs-direct-decode question):

| Image | Full CiMini batch | Isolated (family alone) | Δ |
|---|---|---|---|
| `OMB-E180-BV_1.jpg` | 0.3939 | 0.3701 | -0.024 |
| `OMB-E180-BV_2.jpg` | 0.4707 | 0.5077 | +0.037 |
| `OMB-E180-BV_3.jpg` | 0.3993 | 0.3997 | +0.0004 |
| `OMB-E180-BV_4.jpg` | 0.4521 | 0.4968 | +0.045 |

Every `BACK`-classified image in the family shifted, by up to 0.045 — roughly 10x the ticket's own
headline 0.39-vs-0.40 near-tie gap that started this investigation. `_1.jpg` (the image already
flagged above as the deciding tie-break winner in the `PipelineFixture` transport) shifted from 0.394
(full batch) to 0.370 (isolated) — a real, measurable, same-transport change. **This confirms CLIP
inference in `ImageClassifier`/`ClassificationService` is sensitive to batch composition** — a
previously undocumented defect, now measured. Both runs used the identical in-process transport, so
this is not (or not only) the transport-decode-path question originally framed — it reproduces from
batch composition alone, before transport is even a variable.

**Likely mechanism, not yet verified at the code level:** `ImageClassifier.ClassifyImages`
(`ImageClassifier.cs:182-218`) batches multiple images into one `[B,3,H,W]` tensor and shares one
`InferenceSession.Run` amortizing the text branch — `ClassifyImage`/`ClassifyImages` are otherwise
fully deterministic per call (single Run on a fixed tensor, no dropout/sampling). Floating-point
summation inside the ONNX graph is not strictly associative, so a batched Run over N images can
legitimately produce different per-image logits than the same image run alone or in a
differently-composed batch.

**User direction, 2026-08-11 — the magnitude changes the fix, not just the framing.** Max single-image
delta measured: 0.045 (`_4.jpg`). Full signed range across the batch: 0.069 (`_1.jpg` at -0.024 to
`_4.jpg` at +0.045). Against the current `hero-orientation` threshold of **0.33**
(`Prism_Config.json`'s `Confidence_Thresholds`), every measured value (0.370-0.508) clears the bar by
only 0.04-0.18 — the jitter band and the threshold's safety margin overlap. **User's read: this
magnitude is negligible in absolute terms and does not justify chasing the ONNX/batching mechanism
itself — the right fix is calibrating thresholds toward "only certain acceptance," i.e. raising the
bar enough that batch-composition jitter can no longer flip an accept/reject or a near-tie winner.**
Chasing strict batch-order determinism in the ONNX graph is out of scope unless calibration alone
proves insufficient.

## The batch-removal alternative — measured, costed, rejected (2026-08-12)

A separate agent session investigated this ticket on 2026-08-07, four days before the step-3 threshold
decision, and reached the opposite conclusion: fix the batching itself. That work was never merged —
its measurements are folded in here because they are the strongest evidence the step-3 decision has,
and because two of them are sharper than anything above. The code lives on tag
**`t-2840-batch-removal-rejected`** (`git show t-2840-batch-removal-rejected`); no branch remains.

**Sharper evidence 1 — it is composition, not batch size.** Step 1's table above compares a full
~85-image batch against the family in isolation. That comparison cannot separate "batch size changed"
from "batch contents changed", because both changed at once. The 2026-08-07 session held **batch size
fixed at 8** and varied only which filler images shared the batch:

| Condition (all `OMB-E180-BV_1.jpg`) | `hero-orientation` |
|---|---|
| Isolated, batch of 3 (family alone) | 0.3617 |
| Batch of 8, filler set A | 0.3789 |
| Batch of 8, filler set B — same size, different images | 0.3916 |
| Full ~85-image JBComplete run | 0.3939 |

Rows 2 and 3 are the crux: identical batch size, different neighbours, different answer. Batch size is
not the variable — **batch membership is**. `model_uint8.onnx` is a uint8-quantized export, and
quantized graphs derive scaling ranges from the tensor handed to them, so a shared `[B,3,224,224]`
input makes each image's logits depend on every other image in it. That is the mechanism step 1 above
lists as "likely, not verified"; this rules in composition-dependence specifically and rules out
float-summation-order-over-N as a sufficient explanation on its own.

**Sharper evidence 2 — the fix works, exactly.** With `ClassifyImages` issuing one `Run` per image,
all four conditions above returned **bit-for-bit identical** values (`_1` = 0.35094504799070764,
`_3` = 0.3556184682640039) across isolated, both 8-image padded runs, and the full 85-image run.
Composition, size and transport stop mattering entirely. So the root-cause fix is available and
demonstrably total — it was rejected on price, not on doubt.

**The price, measured on the same dataset and machine.** Import+Match only, before/after:
**1m 24s → 4m 18s (≈3.1×)**. The cause is structural, not incidental: this CLIP export is entangled —
one `Run` must carry the image tensor *and* all 34 prompt tensors together (see `ImageClassifier.cs`'s
`ClassifyImage` remark). Batching's entire benefit is amortizing the 34-prompt, 77-token, 12-layer text
branch across a chunk of 8; one Run per image restores it to once per image. `RunLock` serializes every
`Run` anyway, so this cannot be parallelized away. At ~85 images that is ≈+2s/image; extrapolated
linearly (an estimate, not a measurement) a 1774-image SMASHEDLEMON45 job goes from ~15 min to ~75 min.
Classify is the documented dominant stage (2026-07-15 SPACINI29 baseline), so the multiplier lands on
the pipeline's most expensive work, not its cheapest.

**Decision, 2026-08-12 (user): keep batching.** Step 3's threshold raise is the accepted fix. Rationale:
the 0.42 bar already absorbs the measured jitter for accept/reject decisions at zero runtime cost, and
per step 4 there is currently **no live matching defect** attributable to this — all four originally-named
families resolved to [[T-5090]]/[[T-5100]] bugs or generic ordering drift. Paying ~3.1× on the
bottleneck stage to fix a phenomenon with no visible victim is the wrong trade at POC stage.

**What this decision does *not* cover — the residual, stated plainly.** Raising the threshold protects
the accept/reject boundary. It does not protect **ranking between two images that both clear it**: two
photos at 0.45 and 0.46 sit closer together than the 0.045 jitter, so which one takes `det0` can still
move between runs and between transports. That is exactly `94613033` (Pareo) and `90861083`. Those stay
[[T-5080]]/[[T-2600]] territory — real classifier separation, not a stability patch.

**Unplanned finding worth keeping: `90861083` (`23211008_02_A.jpg`/`_B.jpg`).** Under the batch-removal
fix this family's `det0`/`det1` swap relative to the committed golden. Both images score `BACK` within a
few hundredths of each other — the same near-tie class as Pareo. Pre-fix, `_B` matched the golden by
coincidence of batch-dependent scoring; post-fix the stable measurement picks the other, equally
unverified, winner. **This is a second concrete instance of the near-tie ordering exposure above, found
on a family this ticket never named** — worth remembering when [[T-5080]] picks up orientation
separation. `expected-manifest.json` was correctly left untouched (no verified ground truth for which
image should be `det0`); on main, with batching kept, this family still passes.

**The fix that would cost nothing, for whoever revisits this.** Batching only helps because the text
branch is redundant work — the 34 prompts never change. A re-exported ONNX graph with a *separate* text
encoder would let prompt embeddings be computed once per process and each image run alone, giving
per-image independence **faster than today's batching**, not 3.1× slower. That needs replacing the model
asset, which `PRISM-classify.md` marks temporary/not-recreatable — out of scope here, but it is the
option that dissolves this tradeoff rather than picking a side of it.

**Relevant to [[T-5200]]:** confirms the mechanism that ticket's "possible interaction" note flagged
as unproven — Bracket 4's candidate set can genuinely shift by a few percent depending on what else is
in the batch, which changes how many images spill into SiblingPropagator. Still not proof the two
compound on a real large dataset (that needs a batch-size-scaled experiment, not done here), but the
underlying instability this depends on is no longer hypothetical.
