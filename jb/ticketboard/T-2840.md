### T-2840 · CLIP classification differs by submission transport for near-tied confidence scores
**Status:** Ready | **Profile:** P4-critical-architecture
**Found by:** widening `PipelineFixture` to submit the full CiMini dataset, 2026-08-06 — see
`test/datasets/CiMini/README.md` history note and [[T-4980]]/[[T-5060]]'s update notes for the merge
context.

CLIP confidence scores for near-tied images differ depending on submission transport (in-process
`PipelineFixture` vs. the HTTP job path in `Invoke-CiPipeline.ps1`), which changes classification and
ordering outcomes for the same logical input. This is [[T-2820]] recurring under an angle T-2820 never
tested — same-transport determinism holds, but two different transports for the same input disagree.
Investigation traced the root cause to CLIP batch-composition sensitivity in the ONNX classifier, not to
ordering/tie-break logic.

**Problem(s):**
- **Transport mismatch reproduces T-2820 under a new angle.** T-2820 ("Ordered stage assigns
  non-deterministic det-slots for tied images") was closed 2026-07-15 as not-reproducing: 3-5 consecutive
  `Invoke-CiPipeline.ps1 -Mode Full -Dataset CiMini` runs (same transport, same process) gave
  byte-identical output every time — confirmed again here. But T-2820 never compared two *different*
  submission transports against each other for the same logical input; this ticket does, and they
  disagree. `CiMiniGoldenTests.CiMini_Manifest_MatchesCommittedGolden` (`dotnet test` via
  `PipelineFixture` — direct in-process `PrismService.Process()` call submitting every image loose)
  mismatches the golden captured by `Invoke-CiPipeline.ps1 -Mode Full -Capture` (a real HTTP job — its
  `Submit-PrismJob` sends exactly one seed image via multipart and repacks every other image, including
  plain top-level loose files, into a synthetic zip uploaded as a second multipart part) on exactly 4
  families beyond the already-known Pareo/94613033 case ([[T-5080]]): `99985047` (`26182-Denim-801/a
  (1).jpg` vs `87186790_2.jpg`), `99147525` (3 `C153KB460011_*.png` files), and `98636303`
  (`OMB-E180-BV_1/2/3.jpg`). Confirmed fully deterministic *within* the `PipelineFixture` transport (3
  repeated `dotnet test` runs, separate processes, byte-identical mismatches every time — matches
  T-2820's own same-transport finding, so this is not random/GPU-jitter-flaky). Read
  `ImageOrderer.ProcessFamily`: overflow ordering sorts purely by `Anchor → OnModelRank →
  InitialFullName (natural comparer) → Index` — filename-content-based, not list-position-based; read
  `Importer.SortDeterministically` (T-2820's own fix) and `MatchingService.MatchAsync`'s indexed
  `results[chunkStart+i]` writes — input order is explicitly normalized to `InitialFullName`-sorted and
  preserved through classification regardless of submission order. So transport-level ordering cannot
  explain this by itself — the tie-break logic is not the bug. Used the evidence-dump harness
  (`.claude/skills/prism-evidence-report/harness/EvidenceDumpHarness.cs` — copy into
  `jb/src/tests/Prism.Core.Tests/`, run, delete after) to inspect family `98636303`: `OMB-E180-BV_1.jpg`
  and `_3.jpg` both resolve to the single candidate phenotype `back-packshot`, both
  `hero-orientation=BACK`, confidence **0.39 vs 0.40** — a near-tie barely above the
  already-documented-fragile 0.33 threshold (`test/datasets/CiMini/README.md`'s "Filename keywords will
  silently decide the answer" section; [[T-5080]]). In the `PipelineFixture` transport `_1` wins the slot
  (deterministic filename-ordinal tie-break, given that candidate set); the ps1-captured golden has `_3`
  winning instead — meaning the *candidate set itself* differed between transports, i.e. actual
  classification output differed for at least one image per affected family. Checked whether
  `ImageSourceKind` (`ZipMember` vs `LocalPath` — the two transports produce different values for the
  same logical image) is consumed anywhere in `Services/Matching`: it is not referenced at all, so it is
  not a direct behavioral switch. User direction on T-2820, still the best lead (2026-07-14): *"the fix
  likely lives in CLIP refinement, not in a tie-break hack. If two images in a family score
  near-identically, that is the classifier failing to distinguish them."* Confidence values this close
  (0.39/0.40, both barely clearing 0.33) are exactly that case — a deterministic secondary tie-break
  (which already exists and works correctly) only freezes an arbitrary winner in place, it doesn't fix a
  classifier that can't tell two images apart. **Investigated further, 2026-08-11 — the original evidence
  stopped being live:** all 4 originally-named families were re-examined against current code. None
  currently show a FamilyId/Status mismatch — only DetOrder/FinalFileName (plain ordering drift).
  `98636303` (`OMB-E180-BV_*`) was [[T-5100]]'s bug (Bracket 3/SiblingPropagator), not CLIP.
  `87186790_1`/`_2.jpg` (families `99984905`/`99985047`) was [[T-5090]]'s bug (SubstringRescue
  ambiguity), not CLIP — both landed and re-blessed 2026-08-11, `expected-manifest.json` now expects
  `Ko`/unmatched for all of these, matching `expected-match.json`'s longstanding correct expectation.
  `99147525` and `99985047`'s remaining member (`26182-Denim-801/a (1).jpg`) show only DetOrder drift now
  too — same category as ~90 other unrelated families in the golden, a pre-existing ordering issue
  ([[T-5120]]'s territory), not a distinguishable CLIP-transport signature. Net: this ticket's original
  evidence has now been explained by other tickets or reduced to generic ordering noise — there is
  currently no live, isolated example of a CLIP-transport-driven *matching* mismatch in the CiMini
  golden. The only surviving hard evidence for the phenomenon itself is the isolated-batch experiment
  below (real and reproducible, but a controlled test, not something visible in the golden run today).
- **Batch-composition sensitivity in the CLIP classifier — confirmed and measured, 2026-08-11 (resolves
  the original what-to-do plan's step 1).** Isolated-batch experiment: family `98636303`
  (`OMB-E180-BV_1..6.jpg`) submitted alone in a scratch `test/datasets/` folder (full
  `Brackets-Complete.xlsx` included, so only the image-batch composition variable changed, not matching
  context) via the evidence harness; `hero-orientation` confidence diffed against the same images'
  values from a fresh full-CiMini run in the same session (same transport, `PipelineFixture` both times —
  isolates batch composition specifically, independent of the transport/ZIP-vs-direct-decode question):

  | Image | Full CiMini batch | Isolated (family alone) | Δ |
  |---|---|---|---|
  | `OMB-E180-BV_1.jpg` | 0.3939 | 0.3701 | -0.024 |
  | `OMB-E180-BV_2.jpg` | 0.4707 | 0.5077 | +0.037 |
  | `OMB-E180-BV_3.jpg` | 0.3993 | 0.3997 | +0.0004 |
  | `OMB-E180-BV_4.jpg` | 0.4521 | 0.4968 | +0.045 |

  Every `BACK`-classified image in the family shifted, by up to 0.045 — roughly 10x the ticket's own
  headline 0.39-vs-0.40 near-tie gap that started the investigation. `_1.jpg` (the image flagged above as
  the deciding tie-break winner in the `PipelineFixture` transport) shifted from 0.394 (full batch) to
  0.370 (isolated) — a real, measurable, same-transport change. This confirms CLIP inference in
  `ImageClassifier`/`ClassificationService` is sensitive to batch composition — a previously
  undocumented defect, now measured. Both runs used the identical in-process transport, so this
  reproduces from batch composition alone, before transport is even a variable. Likely mechanism, not
  yet verified at the code level when first found here: `ImageClassifier.ClassifyImages`
  (`ImageClassifier.cs:182-218`) batches multiple images into one `[B,3,H,W]` tensor and shares one
  `InferenceSession.Run`, amortizing the text branch; floating-point summation inside the ONNX graph is
  not strictly associative, so a batched Run over N images can legitimately produce different per-image
  logits than the same image run alone or in a differently-composed batch — later confirmed and sharpened
  by the batch-removal work, see the Decision below. **Relevant to [[T-5200]]:** this confirms the
  mechanism that ticket's "possible interaction" note flagged as unproven — Bracket 4's candidate set can
  genuinely shift by a few percent depending on what else is in the batch, which changes how many images
  spill into SiblingPropagator. Still not proof the two compound on a real large dataset (needs a
  batch-size-scaled experiment, not done here), but the underlying instability this depends on is no
  longer hypothetical.
- **Unplanned finding, distinct from the above: `90861083` (`23211008_02_A.jpg`/`_B.jpg`) det0/det1
  swap — found on a family this ticket never named.** Under the batch-removal fix (see Decision below),
  this family's `det0`/`det1` assignment swaps relative to the committed golden. Both images score `BACK`
  within a few hundredths of each other — the same near-tie class as Pareo (`94613033`). Pre-fix, `_B`
  matched the golden by coincidence of batch-dependent scoring; post-fix the stable measurement picks the
  other, equally unverified, winner. Worth remembering when [[T-5080]] picks up orientation separation.
  `expected-manifest.json` was correctly left untouched (no verified ground truth for which image should
  be `det0`); on `main`, with batching kept, this family still passes.

**Decision(s):**
- **`hero-orientation` threshold raised 0.33 → 0.42 (decided: 2026-08-11).** Chosen directly from the
  measured jitter (max single-image delta 0.045, signed range 0.069 — from `_1.jpg` at -0.024 to
  `_4.jpg` at +0.045) rather than a fresh labelled-data sweep: 0.42 gives ~0.09 margin over the worst
  measured swing, more than the 0.069 span itself, so batch-composition jitter alone can no longer flip
  an accept/reject decision or a near-tie winner for values that clear the new bar. Follows the
  2026-08-11 user direction that the jitter magnitude (0.045 max delta against a 0.33 bar cleared by only
  0.04-0.18 for the measured range 0.370-0.508, per `Prism_Config.json`'s `Confidence_Thresholds`) is
  negligible in absolute terms and doesn't justify chasing the ONNX/batching mechanism itself —
  calibrating thresholds toward "only certain acceptance" was the chosen direction, with chasing strict
  batch-order determinism in the ONNX graph out of scope unless calibration alone proved insufficient.
  **User-acknowledged tradeoff:** this directly cuts against [[T-5080]], which already found 0.33 too
  *high* in the other direction (37% `UNKNOWN`, `SIDEON` never fires on real data) — raising further
  pushes coverage down more. Decided anyway: T-2840's stability concern takes priority for now; T-5080's
  coverage problem stays tracked separately and gets revisited once orientation prompts/taxonomy are
  reworked there, not by lowering this bar again as a workaround. Prompt wording (`ClipPrompts.json`)
  untouched — the 2026-07-14 direction on prompt clarity (see Problem above) remains open if 0.42 alone
  proves insufficient later. Verification run: see Test(s) below.
- **Keep batching — the root-cause fix (removing batching) was built, measured, and rejected on cost
  (decided: 2026-08-12; this closes the original what-to-do plan's step 2 for good).** A separate agent
  session investigated this ticket on 2026-08-07 (four days before the threshold decision above) and
  reached the opposite conclusion: fix the batching itself. That work was never merged — its measurements
  are folded in here because they're the strongest evidence for this decision. The code lives on tag
  **`t-2840-batch-removal-rejected`** (`git show t-2840-batch-removal-rejected`); no branch remains. It is
  composition, not batch size: the isolated-batch table above compares a full ~85-image batch against the
  family in isolation, which can't separate "batch size changed" from "batch contents changed" since both
  changed at once. The 2026-08-07 session held batch size fixed at 8 and varied only which filler images
  shared the batch:

  | Condition (all `OMB-E180-BV_1.jpg`) | `hero-orientation` |
  |---|---|
  | Isolated, batch of 3 (family alone) | 0.3617 |
  | Batch of 8, filler set A | 0.3789 |
  | Batch of 8, filler set B — same size, different images | 0.3916 |
  | Full ~85-image JBComplete run | 0.3939 |

  Rows 2 and 3 are the crux: identical batch size, different neighbours, different answer — batch size is
  not the variable, batch *membership* is. `model_uint8.onnx` is a uint8-quantized export, and quantized
  graphs derive scaling ranges from the tensor handed to them, so a shared `[B,3,224,224]` input makes
  each image's logits depend on every other image in it. This rules in composition-dependence
  specifically and rules out float-summation-order-over-N as a sufficient explanation on its own. The fix
  works, exactly: with `ClassifyImages` issuing one `Run` per image, all four conditions above returned
  bit-for-bit identical values (`_1` = 0.35094504799070764, `_3` = 0.3556184682640039) across isolated,
  both 8-image padded runs, and the full 85-image run — composition, size and transport stop mattering
  entirely. The fix was rejected on price, not doubt: measured on the same dataset and machine,
  Import+Match only, before/after: **1m 24s → 4m 18s (≈3.1×)**. The cause is structural: this CLIP export
  is entangled — one `Run` must carry the image tensor *and* all 34 prompt tensors together (see
  `ImageClassifier.cs`'s `ClassifyImage` remark). Batching's entire benefit is amortizing the 34-prompt,
  77-token, 12-layer text branch across a chunk of 8; one Run per image restores it to once per image,
  and `RunLock` serializes every `Run` anyway so this can't be parallelized away. At ~85 images that's
  ≈+2s/image; extrapolated linearly (an estimate, not a measurement) a 1774-image SMASHEDLEMON45 job goes
  from ~15 min to ~75 min. Classify is the documented dominant stage (2026-07-15 SPACINI29 baseline), so
  the multiplier lands on the pipeline's most expensive work, not its cheapest. **Decision (user,
  2026-08-12): keep batching.** The 0.42 threshold raise above is the accepted fix — it already absorbs
  the measured jitter (0.069 signed range) for accept/reject decisions at zero runtime cost, and there is
  currently no live matching defect attributable to this (see Problem above: all four originally-named
  families resolved to [[T-5090]]/[[T-5100]] bugs or generic ordering drift). Paying ~3.1× on the
  bottleneck stage to fix a phenomenon with no visible victim is the wrong trade at POC stage. **What this
  does not cover — the residual, stated plainly:** raising the threshold protects the accept/reject
  boundary, not ranking between two images that both clear it — two photos at 0.45 and 0.46 sit closer
  together than the 0.045 jitter, so which one takes `det0` can still move between runs and transports.
  That is exactly `94613033` (Pareo) and `90861083` (see the Problem finding above) — real classifier
  separation work, [[T-5080]]/[[T-2600]] territory, not a stability patch. **Reopening this needs a reason
  to pay ≈3.1× on the Classified stage** — not just a preference for the cleaner mechanism; do not invest
  in ONNX re-export/batch-order determinism work without re-opening this decision first. **The fix that
  would cost nothing, for whoever revisits this:** batching only helps because the text branch is
  redundant work (the 34 prompts never change) — a re-exported ONNX graph with a *separate* text encoder
  would let prompt embeddings be computed once per process and each image run alone, giving per-image
  independence *faster* than today's batching, not 3.1× slower. That needs replacing the model asset,
  which `PRISM-classify.md` marks temporary/not-recreatable — out of scope here, but it's the option that
  dissolves this tradeoff rather than picking a side of it.
- **Whether to still run T-2820's original acceptance bar as a general health check — open, not
  decided.** That bar (5 consecutive `-Mode Full -Dataset CiMini` runs, byte-identical, plus a
  cross-transport check) made sense when 4 concrete families were in hand to check against. With none
  left in that shape (see Problem above), running it now would mostly re-confirm ordering drift that's
  already known and tracked ([[T-5120]]), not test transport-sensitivity specifically. Needs a decision:
  close this ticket on "batch-composition sensitivity is confirmed and threshold-calibrated, no
  currently-visible matching defect remains to re-verify" — or run the bar anyway as a general health
  check regardless. Not run this session; flagged rather than guessed.
