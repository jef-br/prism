## Behavioral Memory

Resolved decisions and gotchas agents should know before touching code:

- **ONNX singleton**: migration to application-scoped singleton is an *answered* decision — do not re-open. Implemented (done 2026-06-29, per M5 milestone gate): `MatchingService` owns one shared `ImageClassifier` (`_sharedClassifier`) for the job's lifetime, handed to every `ClassificationService`; a `_clipLock` serializes `InferenceSession.Run()` calls.
- **`illustration-technical-drawing` scope**: option (b) accepted — null/no-phenotype. Do not add a phenotype for it.
- **CLIP input_ids**: combined-input `Run()` is the fix for the input_ids inference bug. Already merged. Do not revert to separate runs.
- **Dual-interface contract**: all `Tx_*` processing-tool classes expose `Process(byte[] arr, int stride, float upscale_factor)`. Match this signature exactly.
- **WPF workbench deleted (2026-07-10)**: the web workbench (`jb/src/workbench/web/`) is the only workbench frontend. `Prism.Workbench.Wpf` was removed from `PRISM.sln` and `jb/src/workbench/wpf/` deleted. Do not re-add WPF parity language or web/WPF "allowed differences" — workbench docs are web-only.
- **Core co-deployment (2026-07-15, T-3600; refined by T-3300)**: Ingress + Matching + Export always run on one physical system sharing the job temp folder (the artifact bus). Do not propose shipping normalized image bytes over the wire for Matching; `NormalizedJpgPath` as a local absolute path is the deliberate contract. The four public services (Matching/Generate/Transform/Upscale) may run as their own `Prism.ServiceHost` processes — Matching only co-located on the same filesystem Ingest wrote. Ingest is never a service. See `PRISM-overview.md` "Core vs. Features" and `PRISM-io-import.md` "Co-Deployment Contract".
- **Batch cap is 10000 images / 250 MB per file (2026-07-17)**: `Input.Images.amount.max` in `Prism_Config.json` is 10000, `Input.Images.filesize.max` is 262144000 bytes (250 MB) — a single hard cap, not a two-tier "normal/ceiling" limit. Docs previously said 2500/5000 and 25 MB (stale since the cap was bumped in commit `57da823` without a doc update); `PRISM-overview.md`, `PRISM-information.md`, `PRISM-knowledge-base.md` now match the config. Read the config, not old doc numbers, if this value matters again.
- **Doc sweeps must glob `*.md` and `*.MD` separately**: `jb/docs/ImageNGP/PRODUCTTYPES.MD` uses an uppercase extension; case-sensitive `*.md` globs silently skip it. Confirmed while closing the docs-vocabulary jbtodo (2026-07-17).
- **Unified ONNX Runtime policy (2026-07-20, T-4110)**: single `Microsoft.ML.OnnxRuntime.DirectML` version (`1.24.4`) pinned centrally in `jb/src/Directory.Packages.props` (CPM) — `SixLabors.ImageSharp` and `OpenCvSharp4`/`OpenCvSharp4.runtime.win` are pinned the same way, same file. Every `InferenceSession`/`SessionOptions` in PRISM (CLIP, YOLO, Upscale, and any future model-running code) must be constructed via `OnnxSessionFactory.Create(modelPath)` (`jb/src/core/Services/Matching/OnnxSessionFactory.cs`) — never inline. Enforced by the conventions hook's `onnx-session-bypass` category. Corollaries (same day, user): no algorithm switching on GPU presence (models load on every host; the factory picks the EP), and missing **or corrupt** model assets fail startup loud for all three models — existence via `ValidateModelAssets`/`ResolveClassifierPaths`, corruption via `PrismConfigurationException` thrown from each loader's `Initialize` (contract pinned by corrupt-file tests in all three suites). The Lanczos CPU-fallback upscaler and `ImageUpscaler` router were deleted; single `Upscaler` class remains. See `jb/docs/PRISM-model-runtime.md`.

- **Backgrounded commands inside a subagent don't reliably notify (2026-07-24)**: a subagent that runs a long command (`dotnet test`, a build) via a backgrounded Bash call and ends its turn promising to "report back when done" can leave that promise permanently unfulfilled. The completion event for a Bash task backgrounded *inside* a subagent's own context does not reliably wake that subagent back up, even though the equivalent works at the top-level session. Confirmed 2026-07-24: a subagent launched the ~6-minute Match test suite in the background and ended its turn expecting to resume on completion; the process silently died with no completion event ever firing, and the caller waited over an hour before anyone noticed. Rule: any agent (orchestrator or subagent) running verification that takes more than a minute or two must either (a) run it in the foreground/blocking within the same turn, or (b) if it must be backgrounded, actively re-check its own output/process state before ending the turn — never end a turn on an unconfirmed background promise.

- **Model/asset *paths* are config, not "structure" (2026-07-31, user)**: the no-magic-values rule bites on file paths and asset identifiers, not just numeric tuning values. Found live: the YOLO26 path `Services/Matching/Analyzers/ONNX/yolo26s.onnx` was hardcoded in `FeatureAnalysisService.cs` **and** again in `PrismConfiguration.ValidateModelAssets`, plus a third time in prose inside both exception messages — while CLIP and Real-ESRGAN correctly read theirs from `Prism_Config.json`'s `Models` section. Two failure modes this rule prevents: the startup validator and the runtime consumer can drift apart silently (one passes, the other throws), and relocating a model means finding every literal. Now `Models.Yolo.Path`. **Two habits that produce this defect — check for both:** (1) a path feels like a structural fact about the repo rather than a parameter, so it slips past a filter that is mentally applied to thresholds; and (2) `ModelAssetLocator.Find("literal")` reads as already-abstracted because the *resolution* is abstracted, when it is the *value* that must come from config. Corollary: inheriting a hardcode from surrounding code when editing an existing file is not an exemption — if you touch the line, fix it or ticket it.
