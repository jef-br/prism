**Both dormant defects from item 5 confirmed live.**

1. *`FinalOutputSize.RoutesToCenterAndStretch` disagrees with actual routing.* It reads
   `lambda.BoundingBox is not null && !HasEdgeIntersect(lambda.Features)` (`FinalOutputSize.cs:32-34`)
   with no phenotype check, while `SelectTransformer` Step 1 (`ImageTransformer.cs:113`) sends
   `BoundingBox is null || SelectedPhenotype is null` to `Tx_ProblemImageProcessor`. Its two consumers
   are `ApplyShadowAccounting` (`ImageTransformer.cs:82`) and upscale sizing
   (`ImagePreProcessor.cs:230-231`). **Effect:** for a bbox + no-intersect + null-phenotype image the
   pipeline shadow-trims a box nothing will read and computes a centre-and-stretch canvas target for a
   route the image will not take. **Consequence:** wrong sizing decisions, not wrong pixels —
   `Tx_ProblemImageProcessor.Process()` reads real dimensions off the loaded bytes.
2. *`Tx_ProblemImageProcessor` reports pre-upscale dimensions.* `Transform` calls
   `ComputeSafeResizeTarget(InputImage.Width, InputImage.Height, ...)`
   (`Tx_ProblemImageProcessor.cs:50`), and `ScaleGeometryToUpscaledImage`
   (`ImagePreProcessor.cs:267-278`) deliberately never updates `lambda.Width`/`.Height` — they are "the
   original-resolution contract the upscale manifest reports against". **Effect:**
   `OutputRecord.OutputWidth`/`OutputHeight`/`ScaleFactor` are computed pre-upscale while
   `ProcessedBytes` may already be upscaled. **Consequence:** manifest metadata is wrong for everything
   on this path, which went from rare to common when the bypass was removed.

**Reviewer's own scoping:** the two confirmed defects are already tracked as separate follow-up work and

Reviewing SPACINI29 the user stated the required treatment for the bulk of it: *"horizontally centers the
subject, adjusts the canvas to size it correctly and then adds background by stretching it on each side as
needed."* On SPACINI29 **86 of 86 images touch at least one edge** (16 touch one, 70 touch two), and not
one of them reached that treatment.

**Decision (user, 2026-07-31) — no new `Tx_*` class.** `Tx_CenterAndStretch` is for intersect-free images
only. Opposing-edge intersects (top+bottom, left+right) belong in `Tx_CropSquare`'s existing
centre-then-squarify-then-stretch-background behaviour. This was never a Step-2/Step-3 boundary problem;
the confusion was in prior phrasing of the ticket.

**Root cause:** `BypassPhenotypes = true` in `ImageTransformer.cs` forced **every** edge-intersecting image
— single-edge included — through `Tx_CropSquare`, permanently masking the phenotype/det-slot gate. That,
not the routing shape, is why C&S-intended images never reached their handler and why single-edge images
never reached `Tx_DetailCropper`. Investigation confirmed `Tx_DetailCropper.ApplyDecisionTree` already
handles all 0–4 edge patterns (`ZeroEdges`/`OneEdge`/`TwoOpposing`/`TwoAdjacent`/`ThreeEdges`/`FourEdges`),
its `TwoOpposing` branch already doing centre + `Tx_util_BgStretch` — so no new predicate was needed in
`FinalOutputSize`.

**Fix committed 2026-07-31 (`416ae33`):** `BypassPhenotypes` and its dead branches removed from
`ImageTransformer.cs`; Step 1's null-`SelectedPhenotype` guard restored. No changes to `FinalOutputSize.cs`,
`Tx_CenterAndStretch.cs` or `Tx_CropSquare.cs` — routing now flows through code that was already there but
unreachable. The [[T-4980]] work it was waiting on landed first (`d808398`), so the merge concern is closed.
