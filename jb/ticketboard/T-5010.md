### T-5010 · Centre-and-stretch was unreachable for the images that need it most
**Status:** Active (2026-08-12) | **Profile:** P4-critical-architecture
**Review:** Request Changes (2026-07-31)
**Found by:** user observation during [[T-4970]], 2026-07-30

A bypass flag masked the phenotype/det-slot routing gate in the Transform stage, so every edge-intersecting
image — the majority of real batches — fell through to the wrong handler regardless of intent. Restoring
the gate exposed two sizing defects it had been hiding, a stale routing spec in this ticket's own text, and
a full rework of `Tx_DetailCropper` to match the user's intended per-edge routing. One re-verification
against a user-blessed ground-truth routing list is still open and is the one thing blocking Done.

**Problem(s):**
- Reviewing SPACINI29, the user stated the required treatment for the bulk of it: *"horizontally centers
  the subject, adjusts the canvas to size it correctly and then adds background by stretching it on each
  side as needed."* On SPACINI29 **86 of 86 images touch at least one edge** (16 touch one, 70 touch two),
  and not one of them reached that treatment. **Root cause:** `BypassPhenotypes = true` in
  `ImageTransformer.cs` forced every edge-intersecting image — single-edge included — through
  `Tx_CropSquare`, permanently masking the phenotype/det-slot gate; that, not the routing shape, is why
  centre-and-stretch-intended images never reached their handler and single-edge images never reached
  `Tx_DetailCropper`. Investigation confirmed `Tx_DetailCropper.ApplyDecisionTree` (`Tx_DetailCropper.cs:143-152`)
  already handled all 0–4 edge patterns (`ZeroEdges`/`OneEdge`/`TwoOpposing`/`TwoAdjacent`/`ThreeEdges`/`FourEdges`),
  reachable and mutually exclusive. **Fixed 2026-07-31 (commit `416ae33`):** `BypassPhenotypes` and its dead
  branches removed from `ImageTransformer.cs`, Step 1's null-`SelectedPhenotype` guard restored; no changes
  needed to `FinalOutputSize.cs`, `Tx_CenterAndStretch.cs` or `Tx_CropSquare.cs` since routing now flows
  through code that already existed but was unreachable. The [[T-4980]] work this was waiting on landed
  first (`d808398`), so the merge concern is closed.
- The ticket's own text made two separate incorrect claims about which class does centre + background-stretch,
  each corrected on a different date. **(a)** The 2026-07-31 decision text claimed opposing-edge intersects
  belong in "`Tx_CropSquare`'s existing centre-then-squarify-then-stretch-background behaviour" —
  **corrected 2026-08-07:** `Tx_CropSquare` has no such behaviour at all. `ComputeCenteredSquareCrop`
  (`Tx_CropSquare.cs:96-99`) takes `side = min(width, height)` at dead centre of the *canvas*, never reads
  `BoundingBox`, and calls `Tx_util_BgStretch` nowhere in the file — its own summary says "Crops the image
  to a square without background extension," so anything routed there gets whatever the canvas centre
  happens to contain. **(b)** The root-cause writeup separately claimed `Tx_DetailCropper`'s `TwoOpposing`
  branch "already does centre + `Tx_util_BgStretch`" — the 2026-07-31 reviewer verified this with a
  correction: `ApplyDecisionTree`'s coverage of all 0–4 edge patterns is confirmed correct and mutually
  exclusive, but `TwoOpposing` (`Tx_DetailCropper.cs:224-253`, pre-rework) only centred and background-stretched
  in one of its three branches (`delta > 0` and within the `_extensionBiDirectional` budget); `delta <= 0`
  cropped, and over-budget did a local square crop — true but narrower than the ticket's claim implied. (The
  reviewer labelled this correction "item 4," which does not match the topic of verification item 4 in this
  ticket's own numbered list, i.e. the null-phenotype watch below — likely a mislabel in the source; preserved
  as found rather than reinterpreted.) Both (a) and (b)'s underlying mechanisms were superseded by the
  2026-08-11 `Tx_DetailCropper` rework, which rewrote `OneEdge`/`TwoOpposing` entirely and removed the
  coverage/budget caps discussed in (b).
- *Dormant defect 1:* `FinalOutputSize.RoutesToCenterAndStretch` disagreed with actual routing. It read
  `lambda.BoundingBox is not null && !HasEdgeIntersect(lambda.Features)` (`FinalOutputSize.cs:32-34`) with
  no phenotype check, while `SelectTransformer` Step 1 (`ImageTransformer.cs:113`) sent
  `BoundingBox is null || SelectedPhenotype is null` to `Tx_ProblemImageProcessor`. Its two consumers were
  `ApplyShadowAccounting` (`ImageTransformer.cs:82`) and upscale sizing (`ImagePreProcessor.cs:230-231`).
  **Effect:** for a bbox + no-intersect + null-phenotype image, the pipeline shadow-trimmed a box nothing
  would read and computed a centre-and-stretch canvas target for a route the image wouldn't take.
  **Consequence:** wrong sizing decisions, not wrong pixels — `Tx_ProblemImageProcessor.Process()` reads
  real dimensions off the loaded bytes. Confirmed live by the 2026-07-31 review (also the concrete proof
  behind the six failing fixture tests, see Test(s)). 2026-08-07 decision: fix in this ticket, reversing the
  reviewer's own scoping. **Superseded 2026-08-12:** closed as superseded, not done-as-written — the
  2026-08-11 `Tx_DetailCropper` rework removed the phenotype/det-slot gate in front of it entirely, so
  phenotype dropped out of routing altogether and there's nothing left for that condition to guard against.
- *Dormant defect 2:* `Tx_ProblemImageProcessor` reports pre-upscale dimensions. `Transform` calls
  `ComputeSafeResizeTarget(InputImage.Width, InputImage.Height, ...)` (`Tx_ProblemImageProcessor.cs:50`),
  and `ScaleGeometryToUpscaledImage` (`ImagePreProcessor.cs:267-278`) deliberately never updates
  `lambda.Width`/`.Height` — described as "the original-resolution contract the upscale manifest reports
  against." **Effect:** `OutputRecord.OutputWidth`/`OutputHeight`/`ScaleFactor` are computed pre-upscale
  while `ProcessedBytes` may already be upscaled. **Consequence:** manifest metadata is wrong for everything
  on this path — on roughly 57 of 86 SPACINI29 images, an upscaled fallback image reports its original size
  and `ScaleFactor` 1.0 while the delivered file is larger; this went from rare to common once the bypass
  was removed. Confirmed live by the 2026-07-31 review. 2026-08-07 decision: fix in this ticket, reversing
  the reviewer's own scoping. **Superseded 2026-08-12:** split out to [[T-5140]] as a separate issue — still
  live there, but the 2026-08-11 `Tx_DetailCropper` rework shrank its blast radius a lot (that path is now
  reached only on a null bbox, not on ~57/86 images), so it no longer sits on this ticket's critical path.
- Item 5 flag-removal hygiene (2026-07-31 review): mostly clean — zero `BypassPhenotypes` references remain
  anywhere under `jb/`, no orphaned config keys, no unreachable branches. One stale doc found outside this
  diff's scope: `Classify/jbtodo.md:13` still says "once T-4970 lands and the BypassPhenotypes flip is
  decided," which already happened here.

**Decision(s):**
- User decision, 2026-07-31: no new `Tx_*` class needed — `Tx_CenterAndStretch` is for intersect-free images
  only; opposing-edge intersects (top+bottom, left+right) route through the existing
  centre-then-squarify-then-stretch-background handling. This was never a Step-2/Step-3 boundary problem;
  the confusion was in prior phrasing of the ticket. (The specific claim that `Tx_CropSquare` was that
  existing handler was itself wrong — see the Problem bullet on the ticket's two incorrect claims — and the
  concrete routing was subsequently redefined by the 2026-08-07/2026-08-11 decisions below.)
- Ground-truth gate, decided/established 2026-08-07: do not close this ticket until
  `spacini29-image-routing-list.md` carries a user-blessed intended route for every SPACINI29 image. Done —
  the user filled in Route-1/Route-2 for all 86 rows; that column is blessed ground truth that the routing
  work is measured against, and no agent may write to it or infer it. (File added by this decision:
  `spacini29-image-routing-list.md`, repo root.)
- User decision, 2026-08-07 (1 of 3 in that block): `body-visible = full` + one edge touched routes to
  `Tx_DetailCropper`, not `Tx_CropSquare`. Intended behaviour, in the user's words: centre the bounding box
  on the axis that has no edge touched, squarify, then background-stretch via `Tx_util_BgStretch` if the
  canvas needed extending. `Tx_DetailCropper.OneEdge` (`Tx_DetailCropper.cs:170-220`, pre-rework) already
  did exactly this — line 181 pinned the touched edge, lines 195-197 centred the free axis on the bbox, line
  217 stretched when the square needed room, line 199 cropped when it didn't; only its gate (closeup
  phenotype + det-slot eligibility) needed to widen to let these images in. **Superseded 2026-08-11:** rather
  than widening the gate, the 2026-08-11 rework (via `/pair`) removed it entirely and rewrote
  `Tx_DetailCropper.OneEdge`/`TwoOpposing` around the routing list's Route-1/Route-2 spec instead —
  margin-anchored axis for the touched edge, bbox-centred free axis, always background-stretch via
  `Tx_util_BgStretch`, no coverage/budget caps. `Coverage`, `ExtensionOneSided`, `ExtensionBiDirectional` and
  `AdjacentCropCap` were removed cleanly from both the code and `transform_Config.json` — nothing orphaned.
  Build clean (14 projects, 0 errors); Transform suite green 86/86. `ImageTransformer.SelectTransformer` no
  longer checks phenotype or det-slot in front of `Tx_DetailCropper` at all — any bbox + any edge intersect
  routes there unconditionally now (see the `JB:` comment at `ImageTransformer.cs:130` pointing at git
  history for how to reinstate a gate if one is ever needed).
- User decision, 2026-08-07 (2 of 3 in that block): both dormant sizing defects are to be fixed in this
  ticket, not deferred to follow-ups — reversing the reviewer's own 2026-07-31 scoping (which held that the
  two confirmed defects were already tracked separately and shouldn't block the commit once the six tests
  were green). **Superseded 2026-08-12:** the `FinalOutputSize`/`SelectedPhenotype` half closed as
  superseded rather than done-as-written; the `Tx_ProblemImageProcessor` half split out to [[T-5140]]
  instead. See the two dormant-defect Problem bullets for full detail.
- User decision, 2026-08-07 (3 of 3 in that block): verification item 3 (spot-check by eye) is answered by
  the routing list, not by manually spot-checking 16 images. Reaffirmed 2026-08-12: item 3 is answered once
  item 2 (the harness re-run) confirms the code matches the routing list. See Test(s).
