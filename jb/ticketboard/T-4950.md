### T-4950 · SubjectMask crosses the service boundary unread
**Status:** Ready | **Profile:** P1-feature-worker
**Found by:** [[T-4800]] completion pass, 2026-07-28

> **Partly overtaken by [[T-5030]], 2026-08-04 — the decision is still open, the framing is not.**
> The `alpha` producer no longer exists: T-5030 deleted `AlphaSubjectCapture` and the whole alpha path,
> so `classical-cv` is now the only thing that encodes a `MaskPng`. That **shrinks** the unread payload
> but does not answer the question — every image still pays a base64 PNG round-trip for something no
> production code reads. Measure against current behaviour, not the two-producer description below, and
> ignore the deleted `AlphaSubjectCapture.cs` in the Files list.

`SubjectDetectionResult.MaskPng` is produced by both producers (`classical-cv` and `alpha` each encode a
full-resolution binary PNG per image) and asserted in tests, but **no production code reads it** —
Transform routes and crops on `Box` plus the intersect flags, and T-4870's evidence deliberately excludes
the pixel mask. **Cause:** built ahead of a v2 consumer (mask-aware fill / seam-carving, deferred).
**Effect:** since [[T-4800]] moved detection into the Classify refinement chain, the mask is created in
Matching and serialized across the Matching→Transform HTTP boundary in a distributed deployment — it
previously never left the process. **Consequence:** every image pays a base64 PNG round-trip for a payload
nothing consumes; on ~1900 images that is real bandwidth for zero benefit.

Not a correctness bug and not urgent. Decide between: keep as-is; `[JsonIgnore]` so it stays in-process;
or gate production behind a config flag until a consumer exists. Measure the per-image payload first.

**Files:** `jb/src/core/Models/SubjectDetectionResult.cs`, `jb/src/core/Services/Matching/SubjectDetector.cs`,
`jb/src/core/lib/Ingress/AlphaSubjectCapture.cs`.
