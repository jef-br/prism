PRISM matching, in depth

How each matching check works under the hood — with a real example that matches, a counterexample that deliberately does not, and the name of the known algorithm behind it.

How to read this page. For every check you get three things:
  • What it does, in plain words.
  • ✔ Example — a real case that matches, and ✘ Counterexample — a case that looks similar but is refused on purpose. The counterexamples matter most: they show the safety rules that keep wrong photos off product pages.
  • Purple badges like Levenshtein distance name the textbook algorithm used, so you can look it up.

0. Two ideas used everywhere

The phone book inverted index

Before matching starts, PRISM builds lookup tables that work like a phone book, but reversed: instead of "product → its numbers", they store "number → which products have it" and "word → which products mention it". Finding all products that contain 60105 is then one instant lookup instead of re-reading the whole Excel for every photo. The same structure powers web search engines.

The one-owner rule

Every check follows the same contract: it may only answer when exactly one product fits. Zero fits → pass the photo to the next check. Two or more fits → also pass it on (and remember the tie). No check ever picks the "most likely" of several candidates. This is why PRISM can be aggressive in finding clues without ever guessing.

This also makes the whole system deterministic: same input, same output, every run. There is no randomness anywhere — no Monte Carlo methods, by design.

1. Entry: removing duplicates dHash (perceptual hashing) Hamming distance

Each photo is shrunk to a tiny 17×8 grid and, for each pair of neighbouring cells, PRISM notes only "is the left one brighter than the right one?". That yields a 128-bit fingerprint of the image's structure, not its pixels — so the same photo saved twice, resized, or re-compressed gets a near-identical fingerprint. Two fingerprints are compared by counting the bits where they differ (Hamming distance); 6 or fewer differing bits means "same picture".

✔ removed as duplicate The batch contains photo.jpg loose and the same picture inside the supplier's zip. Fingerprints differ by 0 bits → the second copy is set aside as a duplicate.
✘ not a duplicate Front view and back view of the same sweater. They show the same product, but their brightness structure differs in far more than 6 bits → both are kept. Also: EU energy labels and technical drawings are exempt, because two labels legitimately look almost identical.

2. The number checks

1Exact number match

Every group of digits in the filename (5 digits or longer) is looked up in the phone book of product numbers, barcodes, references — and every long digit group found anywhere in a product's row, even in the middle of a text cell like MAN-Posy Green-1010930-60105.

✔ match 94671115_2.jpg → digit group 94671115 is exactly one product's number. The 2 is too short to count, so it cannot interfere.
✘ refused: short numbers are ignored Product B has reference MGGE073, which contains the digits 073. The photo 94671115_073.jpg must not hesitate between product 94671115 and product B. Because 3-digit groups are below the 5-digit minimum, 073 is simply not evidence. (Before this rule, over 1,200 photos in one real batch were refused as "fits several products".)

2Numbers glued back together Kendall tau distance dynamic programming

Filenames often split one code into pieces. PRISM concatenates neighbouring digit groups and looks the result up. If nothing fits in the original order, it tries reordered combinations — and scores how much shuffling was needed using the Kendall tau distance (the number of neighbour swaps needed to sort a sequence; also known as bubble-sort distance). Too much shuffling makes the match too far-fetched and it is rejected. Trying orders efficiently uses dynamic programming instead of brute force.

✔ match 24211507_CARDIGAN_76_MAGENTA_B.jpg → 24211507 + 76 in original order equals reference 24211507-76. Zero swaps needed → confident match.
✘ refused: two products, same glue Suppose gluing 12+34 gives 1234, and product A's number is 1234 while product B's barcode also contains exactly 1234. Two owners fit → the one-owner rule blocks the match and the photo moves to the next check.

3The combination lock set intersection

Sometimes each number alone fits many products, but the combination fits one. PRISM takes the candidate list of every number and intersects them — like a combination lock where each digit narrows the possibilities.

✔ match 1010930_60105_A_01.png: colour code 60105 fits 14 products, article 1010930 fits 6 products — but the overlap of both lists is exactly one product. Matched. (This single check rescued ~1,265 photos in the FILA batch.)
✘ refused: the overlap is still two A photo names 1010930 and 60105, but the product exists in two lengths, both with the same article and colour codes. The intersection contains two products → refused, reported as "fits several products" so a human can decide.

3. The word checks

4Words and codes n-grams (bigrams)

Words from the filename are looked up in product descriptions. Three refinements make this robust:

  • Glued words: the index also stores every pair of neighbouring words joined together (a classic n-gram trick), so palmblue finds "PALM BLUE".
  • Codes made of letters+digits: a code like 1707527E that exists in exactly one product may carry a match on its own — normal words may not.
  • Small-number tiebreak: if two products tie on words, a short number in the filename (like colour code 76) may break the tie — but only if it appears in exactly one of the tied products.
✔ match Anastasia_palmblue_2.jpg → "anastasia" + "palmblue" both point to the product described as ANASTASIA AB-PALM BLUE, and no other product scores as high.
✘ refused: common words are not identity blue-shirt.jpg where twenty products are blue shirts. "blue" and "shirt" fit all twenty equally → top tie → refused. A single ordinary word (even a unique one, like a colour that happens to appear once) is also refused, because one common word is weak evidence — only unique letter+digit codes may stand alone.

5What the AI saw CLIP neural network cosine similarity softmax

A vision model (CLIP) converts the photo and a set of short descriptions ("a photo of a dress", "a red product", …) into points in the same mathematical space; the closer the photo lands to a description (cosine similarity), the better it fits. Scores across the options are turned into percentages with softmax, and only confident winners count. Those impressions (product type, colour) are used to rule out products — only among products that received no photos at all.

✔ match An unnamed photo shows a red bag. Of the three products still without photos, one is a red bag, one a green scarf, one a white mug. The type and colour impressions eliminate two; a leftover filename clue confirms the third. Matched.
✘ refused: "last one standing" is not evidence Only one product is left without photos, and an unnamed photo has no AI impression and no filename clue at all. It would be convenient to hand the photo to the last product — PRISM refuses. Being the only candidate is not the same as being pointed at by evidence.

4. The last resorts

6The Excel names the file

If the photo's own filename appears in exactly one product's row (photo-link columns are common), that settles it. The comparison forgives capitals, spaces, dashes, dots and copy markers like  (1) or _RET (retouched).

✔ match Cell: /medias/92836758_det815.jpg. Photo: 92836758_det815 (1).jpg. After normalising both sides they are identical → matched.
✘ refused: two rows name the same file Two products of a set share one packshot, and both rows link to set-photo.jpg. The file is named by two rows → ambiguous → refused rather than guessed.

7Number hidden inside a longer number substring search

A long filename number (7+ digits) is searched for inside product numbers, because article references are often embedded in barcodes.

✔ match 46271023.jpg → 46271023 sits inside barcode 8446271023117 of exactly one product.
✘ refused: too short, or found twice 12345.jpg is never tried (5 digits could sit inside hundreds of barcodes by chance — the minimum is 7). And a 7-digit number found inside two different barcodes is refused by the one-owner rule.

8Copying from a sister photo token-set comparison

Photos of one product usually share the same rare words. PRISM reduces every filename to its rare words (dropping shot markers like _A, _01, (1), and words that half the batch shares, like the brand name). It then works in two steps:

  • Same shot set (strongest). If a photo's word set is exactly the set already shared by matched photos that all belong to one product, this photo is simply the next shot of that product and joins it.
  • Loose overlap (fallback). Otherwise, a photo may inherit a product whose matched photos' word set contains — or is contained by — its own, but only if all such related photos agree on one product.
✔ the whole set is accepted 24211507_..._A.jpg and _B.jpg matched product 90861052; both reduce to {cardigan, magenta}. The keyless third shot CARDIGAN_MAGENTA76_C.jpg reduces to the same set → it is the product's third photo and joins 90861052 too. The ordering step then places the shots (front → det0, back → det1, this one → the next free slot).
✘ refused: the set belongs to two products If the batch genuinely holds two different magenta cardigans, both reducing to {cardigan, magenta}, then that word set is owned by two products at once. A keyless CARDIGAN_MAGENTA_C.jpg cannot tell which one it belongs to → reported, not guessed. Better a gap than a coin flip.

5. Before matching: borrowing a name from the folder

Meaningless filenames get a name from their folder

Some photos arrive with names that say nothing about the product: 1.jpg, DSCN2365.jpg, IMG_10005.png. Before any check runs, PRISM looks at the folder such a photo sits in. It borrows the folder's name only when the folder is meaningful, and all three of these are true:

  • The neighbouring folders (same level) follow the same one-folder-per-product pattern — not a handful of format buckets.
  • The folder name is not a format word like HD, Web, packshot or a size like 800 x 1200.
  • At least one word or code in the folder name actually appears in the Excel data.

When borrowed, the folder name is only used for matching — the photo keeps its real filename in the output and report.

✔ borrowed 1.jpg inside folder earphones_zenith_SH23005, alongside folders earphones_apex_SH23006, … The code SH23005 appears in the Excel, so the photo is matched as if it were named earphones_zenith_SH23005 1.jpg.
✘ not borrowed 1.jpg inside folder HD (or Web, or 800 x 1200). These describe format, not product, so nothing is borrowed and the photo takes its chances on its own name. Also: a folder whose words appear nowhere in the Excel is not borrowed either — it would add noise, not meaning.

6. The Excel side has algorithms too

Forgiving header reading Levenshtein distance

Column titles are compared with known names (in six languages) using edit distance — the number of single-letter changes needed to turn one word into another. One letter of difference is accepted as a typo.

✔ understood A header Famliyid (letters swapped) is 2 edits from familyid… too far — but Familid (1 letter missing) is 1 edit away and is accepted as the product-number column.
✘ not forced A header Family price contains the word "family" but the column holds prices, not 8-digit product numbers. The cell-pattern check (every value must look like a product number and be unique) stops it from being crowned the product-number column.

Rescuing rows without a product number key join

Rows from sheets that lack a product-number column are matched to known products through shared codes — first by barcode, then by any long digit run both sides share. This is the same idea as a database join, done on messy real-world keys.

✔ joined Catalogue row: article 106297094700, no product number. Bundle file: the ref cell 106297094700|… belongs to product 98985645. The row's colour and name now enrich that product.
✘ left aside The article code appears in the ref cells of two products (a single item and a 2-pack). Joining would be a guess → the row stays unjoined and is listed in the report.

7. Famous-algorithm scorecard

Which well-known techniques are inside PRISM — and which famous names are deliberately not:

AlgorithmUsed?Where / why not
Inverted indexYesAll lookup tables: numbers, words, filenames. Same structure as a search engine.
Levenshtein (edit) distanceYesTypo-tolerant Excel header recognition (1 edit allowed).
Kendall tau distanceYesScores how shuffled the digit groups are in check 2's reordered pass.
Dynamic programmingYesFinds the least-shuffled reordering without trying every permutation.
n-grams (bigrams)YesGlued-word matching: "palm"+"blue" indexed as "palmblue".
Perceptual hashing (dHash) + Hamming distanceYesDuplicate photo detection: 128-bit structure fingerprint, ≤6 differing bits = same picture.
CLIP + cosine similarity + softmaxYesThe AI impression of type and colour used in check 5 and for photo ordering.
Set intersectionYesCheck 3's combination lock.
Greedy assignmentYesPhoto ordering: best photo per position, decided position by position.
Hungarian algorithmNoThe optimal-assignment classic. Overkill here: with stable tie-breaks, greedy ordering gives the same result at a fraction of the complexity.
Monte Carlo methodsNoNo randomness anywhere — the same batch must give the same output every run, so results can be audited and compared.
Manhattan / Euclidean distanceNoGeometric distances don't fit this problem; the distances that matter here are edit distance (letters), Kendall tau (order) and Hamming (bits).

8. The design principles behind all of it

  • Certain before clever. Exact numbers → combined numbers → words → AI. Each check is cheaper to trust than the next; the confident checks get the first shot.
  • Every check can say "I don't know." The counterexamples above are not failures — they are the system declining to gamble. A refused photo with a clear reason costs a minute of human time; a wrong photo on a live product page costs much more.
  • Evidence, not elimination. Being the only remaining candidate never wins on its own; something must actively point to the product.
  • Auditable. The report names the check that matched every photo, so any match can be re-explained a month later.
